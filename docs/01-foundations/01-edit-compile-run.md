# 편집, 컴파일, 실행

C 프로그램을 작성할 때는 문법과 함께 **소스 코드가 실행 파일이 되는 과정**을 먼저 이해해야 합니다.

소스 파일을 수정했다고 해서 이미 만들어진 실행 파일의 내용까지 자동으로 바뀌지는 않습니다. 변경 사항을 실행 파일에 반영하려면 소스 파일을 저장한 뒤 다시 빌드해야 합니다.

또한 다음 세 가지는 서로 다른 문제입니다.

- 소스 코드가 컴파일되는가?
- 실행 파일이 정상적으로 만들어지는가?
- 만들어진 프로그램이 의도한 대로 동작하는가?

컴파일과 링크에 성공했다는 것은 실행 파일을 만들 수 있었다는 뜻일 뿐, 프로그램의 동작이 올바르다는 뜻은 아닙니다.

## 가장 작은 프로그램

```c
#include <stdio.h>

int main(void) {
    puts("hello");
    return 0;
}
```

파일 이름을 `hello.c`로 저장했다면 다음과 같이 실행 파일을 만들 수 있습니다.

```sh
cc -std=c11 -Wall -Wextra -Wpedantic hello.c -o hello
```

컴파일과 링크가 성공하면 현재 디렉터리에 `hello`라는 실행 파일이 만들어집니다.

```sh
./hello
```

출력은 다음과 같습니다.

```sh
hello
```

`hello`가 아니라 `./hello`라고 실행하는 이유는 셸의 명령 검색 방식 때문입니다.

셸은 명령을 입력받으면 일반적으로 `PATH` 환경 변수에 등록된 디렉터리에서 실행 파일을 찾습니다. 현재 디렉터리 `.`은 보통 `PATH`에 포함되어 있지 않습니다.

따라서

```sh
hello
```

는 `PATH`에 있는 `hello`를 찾으라는 뜻이고,

```sh
./hello
```

는 **현재 디렉터리에 있는 `hello`를 실행하라**는 뜻입니다.

## 소스 코드에서 실행 파일까지

간단한 명령 하나로 실행 파일을 만들더라도 내부적으로는 여러 단계가 수행됩니다.

```text
hello.c
  ↓
전처리
  ↓
컴파일
  ↓
어셈블
  ↓
오브젝트 파일
  ↓
링크
  ↓
실행 파일
```

각 단계의 역할은 다음과 같습니다.

- **전처리**: `#include`, `#define`, 조건부 컴파일 등의 전처리 지시문을 처리합니다.
- **컴파일**: 전처리된 C 코드를 분석하고 기계어로 변환하기 위한 코드를 생성합니다.
- **어셈블**: 생성된 어셈블리 코드를 오브젝트 파일로 변환합니다.
- **링크**: 여러 오브젝트 파일과 필요한 라이브러리를 결합하여 최종 실행 파일을 만듭니다.

일반적인 개발에서는 이 과정을 각각 직접 실행하지 않고 `cc` 같은 **컴파일러 드라이버**가 필요한 프로그램을 순서대로 호출하도록 합니다.

## 컴파일 명령 읽기

```sh
cc -std=c11 -Wall -Wextra -Wpedantic hello.c -o hello
```

각 부분의 의미는 다음과 같습니다.

- `cc`: 시스템에서 기본 C 컴파일러 드라이버로 설정된 프로그램을 실행합니다.
- `-std=c11`: C11 표준을 기준으로 C 코드를 해석하도록 요청합니다.
- `-Wall`: 자주 문제가 되는 여러 항목에 대한 경고를 활성화합니다.
- `-Wextra`: `-Wall`에 포함되지 않은 추가 경고를 활성화합니다.
- `-Wpedantic`: 선택한 C 표준을 벗어나는 코드에 대해 추가로 경고합니다.
- `hello.c`: 빌드할 입력 소스 파일입니다.
- `-o hello`: 최종 출력 파일의 이름을 `hello`로 지정합니다.

`-Wall`이라는 이름 때문에 "모든 경고"를 활성화한다고 오해하기 쉽지만 실제로 모든 가능한 경고를 켜는 옵션은 아닙니다.

경고는 오류와 다릅니다. 컴파일러는 경고가 있어도 실행 파일을 만들 수 있습니다.

그러나 다음과 같은 경고는 실제 버그를 나타낼 수 있습니다.

- 초기화하지 않은 값 사용
- 잘못된 타입 변환
- 함수 반환값 누락
- 사용하지 않는 변수
- 부호가 다른 정수 타입 비교

따라서 경고를 단순히 없애는 것이 아니라 **왜 발생했는지 이해하고 원인을 수정하는 것**이 중요합니다.

## 컴파일과 링크를 구분하기

여러 소스 파일을 사용하는 프로그램에서는 컴파일과 링크의 차이가 더 분명하게 드러납니다.

예를 들어 다음 두 파일이 있다고 가정합니다.

```sh
main.c
parse.c
```

각각을 오브젝트 파일로 만들 수 있습니다.

```sh
cc -std=c11 -Wall -Wextra -Wpedantic -c main.c
cc -std=c11 -Wall -Wextra -Wpedantic -c parse.c
```

결과는 다음과 같습니다.

```sh
main.o
parse.o
```

`-c` 옵션은 최종 실행 파일까지 만들지 않고 오브젝트 파일까지만 생성하라는 뜻입니다.

두 오브젝트 파일을 연결하면 실행 파일을 만들 수 있습니다.

```sh
cc main.o parse.o -o program
```

따라서 **컴파일 성공과 링크 성공은 별개의 단계**입니다.

각 소스 파일이 올바르게 컴파일되어도 필요한 함수 정의를 링크 단계에서 찾지 못하면 최종 실행 파일은 만들어지지 않습니다.

## 종료 상태 확인하기

프로그램이 종료되면 운영체제는 호출한 프로세스에 **종료 상태(exit status)**를 전달합니다.

`main`에서 반환하는 값이 이 종료 상태로 사용됩니다.

```c
int main(void) {
    return 42;
}
```

프로그램을 실행한 직후 셸에서 다음과 같이 확인할 수 있습니다.

```sh
./program
printf '%s\n' "$?"
```

출력:

```sh
42
```

`$?`는 **가장 최근에 실행된 명령의 종료 상태**를 의미합니다.

따라서 다음처럼 다른 명령을 먼저 실행하면 안 됩니다.

```sh
./program
echo hello
printf '%s\n' "$?"
```

이 경우 `$?`에는 `./program`이 아니라 바로 앞에서 실행한 `echo`의 종료 상태가 들어 있습니다.

Unix 계열 프로그램에서는 일반적으로 다음 규칙을 사용합니다.

```text
0       성공
0 이외  실패 또는 특별한 상태
```

예를 들어 프로그램이 명령행 인자를 잘못 받았을 때 `2`를 반환하도록 정할 수 있습니다.

```c
if (argc != 2)
    return 2;
```

구체적인 실패 값의 의미는 프로그램이 정합니다.

이 때문에 호출자는 화면에 출력된 문자열만 보는 것이 아니라 종료 상태를 사용해 프로그램의 성공 여부를 자동으로 판단할 수 있습니다.

예를 들어 셸에서는 다음처럼 사용할 수 있습니다.

```sh
if ./program; then
    echo "success"
else
    echo "failure"
fi
```

## `stdout`과 `stderr`

프로세스에는 기본적으로 여러 개의 열린 파일 디스크립터가 제공되며, 그중 대표적인 것이 다음 세 가지입니다.

```text
0  stdin   표준 입력
1  stdout  표준 출력
2  stderr  표준 오류
```

일반적인 프로그램 결과는 `stdout`에 출력하고, 오류나 진단 메시지는 `stderr`에 출력합니다.

```c
#include <stdio.h>

int main(int argc, char *argv[]) {
    if (argc != 2) {
      fprintf(stderr, "usage: %s <name>\n", argv[0]);
      return 2;
    }

    printf("Hi, %s\n", argv[1]);
    return 0;
}
```

정상 실행:

```sh
./greet Alice
```

```sh
Hi, Alice
```

잘못된 실행:

```sh
./greet
```

```sh
usage: ./greet <name>
```

화면에서는 두 출력이 비슷하게 보이지만 서로 다른 출력 경로를 사용합니다.

다음과 같이 각각 다른 파일로 보낼 수 있습니다.

```sh
./greet Alice > out.txt 2> err.txt
```

여기서

```sh
> out.txt
```

는 파일 디스크립터 `1`, 즉 `stdout`을 `out.txt`로 보내고,

```sh
2> err.txt
```

는 파일 디스크립터 `2`, 즉 `stderr`를 `err.txt`로 보냅니다.

성공한 경우에는 대체로 다음과 같습니다.

```text
out.txt   정상 결과
err.txt   비어 있음
```

실패한 경우에는 프로그램 설계에 따라 다음과 같이 만들 수 있습니다.

```text
out.txt   비어 있음
err.txt   오류 메시지
```

이 구분은 프로그램을 다른 프로그램이나 셸 스크립트에서 사용할 때 특히 중요합니다.

## 결과를 출력하기 전에 입력을 검증하는 이유

다음과 같은 프로그램을 생각할 수 있습니다.

```text
결과 일부 출력
→ 입력 오류 발견
→ 실패 종료
```

이 경우 호출자는 `stdout`에 남은 내용을 정상적인 결과로 처리해야 하는지 판단하기 어려울 수 있습니다.

따라서 가능하다면 다음 순서를 사용합니다.

```text
입력 확인
→ 필요한 작업 수행
→ 성공 여부 확정
→ 결과 출력
```

물론 모든 프로그램이 결과를 한꺼번에 만들 수 있는 것은 아닙니다. 대용량 파일 처리나 스트리밍 프로그램처럼 작업 도중 결과를 출력해야 하는 경우도 있습니다.

따라서 이것은 절대적인 규칙이라기보다 **출력 전에 검증할 수 있는 입력은 먼저 검증한다**는 기본 원칙으로 이해하면 됩니다.

## 셸 인자와 `argc`, `argv`

다음 명령을 실행한다고 가정합니다.

```sh
./program one "two three"
```

셸은 먼저 명령문을 해석하여 인자를 나눕니다.

이 경우 프로그램에는 개념적으로 다음과 같은 값이 전달됩니다.

```text
argc == 3

argv[0] -> "./program"
argv[1] -> "one"
argv[2] -> "two three"
argv[3] == NULL
```

`argc`는 프로그램에 전달된 문자열의 개수입니다.

`argv`는 각 문자열을 가리키는 포인터들의 배열입니다.

```c
int main(int argc, char *argv[])
```

여기서 보통

```sh
argv[0]
```

에는 프로그램을 실행할 때 사용한 이름이나 경로가 들어갑니다.

따라서 다음 명령은

```sh
./program one "two three"
```

셸에서 세 개의 인자로 해석됩니다.

```sh
./program
one
two three
```

`"two three"`에 사용한 따옴표는 C 프로그램이 해석하는 것이 아닙니다.

따옴표는 **셸에게 공백을 포함한 전체 문자열을 하나의 인자로 취급하라고 지시하는 문법**입니다. 셸이 명령을 해석한 뒤에는 일반적으로 따옴표 자체는 제거되고 문자열만 프로그램에 전달됩니다.

따라서 프로그램은 다음 문자열을 받습니다.

```sh
two three
```

다음 문자열을 받는 것이 아닙니다.

```sh
"two three"
```

## `argv[argc] == NULL`

C 프로그램의 명령행 인자 배열에는 중요한 규칙이 하나 더 있습니다.

```c
argv[argc] == NULL
```

즉 유효한 마지막 인자가

```c
argv[argc - 1]
```

이라면 그 다음 포인터는 `NULL`입니다.

예를 들어

```sh
argc == 3
```

이라면

```sh
argv[0]
argv[1]
argv[2]
```

가 실제 인자이고

```sh
argv[3] == NULL
```

입니다.

하지만 일반적으로 인자를 순회할 때는 `NULL`을 찾기보다 `argc`를 기준으로 반복하는 편이 의도가 더 명확합니다.

```c
for (int i = 0; i < argc; i++)
    printf("%s\n", argv[i]);
```

## 수정과 실행 사이의 확인 순서

개발 중에는 다음 순서를 습관화하는 것이 좋습니다.

```text
소스 수정
→ 파일 저장
→ 빌드
→ 오류와 경고 확인
→ 실행
→ stdout 확인
→ stderr 확인
→ 종료 상태 확인
```

특히 코드를 수정했는데 실행 결과가 바뀌지 않는다면 프로그램 논리를 분석하기 전에 빌드 과정부터 확인해야 합니다.

- 수정한 파일을 실제로 저장했습니까?
- 수정 후 다시 컴파일했습니까?
- 컴파일이 실패했는데 이전 실행 파일을 실행하고 있지는 않습니까?
- 빌드 명령에 수정한 소스 파일이 포함되어 있습니까?
- 예상한 경로의 실행 파일을 실행하고 있습니까?
- 같은 이름의 다른 실행 파일을 실행하고 있지는 않습니까?

예를 들어 새 빌드가 실패해도 이전에 성공적으로 만들어진 실행 파일이 디스크에 그대로 남아 있을 수 있습니다.

```text
이전 program 존재
→ 소스 수정
→ 새 컴파일 실패
→ ./program 실행
```

이 경우 실행되는 것은 새 코드가 아니라 **이전에 만들어진 실행 파일**입니다.

따라서 컴파일 명령의 성공 여부를 확인하는 것도 중요합니다.

## 실패 단계 구분하기

문제가 발생했을 때 어느 단계에서 실패했는지 구분하면 원인을 훨씬 빠르게 찾을 수 있습니다.

### 전처리 오류

전처리 단계에서 발생하는 문제입니다.

예:

```c
#include "missing.h"
```

```sh
fatal error: missing.h: No such file or directory
```

주로 다음을 확인합니다.

- 헤더 파일 이름이 올바른가?
- 헤더 파일이 실제로 존재하는가?
- `#include` 경로가 올바른가?
- 필요한 `-I` 옵션이 지정되어 있는가?
- `#if`, `#ifdef`, `#endif` 같은 전처리 지시문이 올바른가?

### 컴파일 오류

전처리된 C 코드를 컴파일러가 올바른 C 프로그램으로 해석하지 못한 경우입니다.

예:

```c
int main(void) {
    int value =
    return 0;
}
```

문법 오류뿐 아니라 타입 규칙 위반 등도 컴파일 단계에서 발견될 수 있습니다.

컴파일러가 많은 오류를 한꺼번에 출력하더라도 위에서부터 무작정 모두 수정할 필요는 없습니다.

앞쪽의 문법 오류 하나가 이후 코드를 잘못 해석하게 만들어 연쇄적으로 여러 오류를 발생시킬 수 있기 때문입니다.

따라서 일반적으로 **가장 먼저 발생한 의미 있는 오류부터 수정하고 다시 컴파일**합니다.

### 링크 오류

각 소스 파일의 컴파일에는 성공했지만 최종 실행 파일을 만들지 못한 경우입니다.

예를 들어 다음처럼 함수를 선언하고 호출했다고 가정합니다.

```c
int parse_input(const char *text);

int main(void) {
    return parse_input("42");
}
```

함수의 실제 정의가 링크 입력에 없다면 다음과 같은 오류가 발생할 수 있습니다.

```sh
undefined reference to `parse_input'
```

이 경우 확인할 것은 C 문법이 아니라 다음과 같은 항목입니다.

- `parse_input`을 구현한 소스 파일을 빌드했는가?
- 해당 오브젝트 파일을 링크 명령에 넣었는가?
- 필요한 라이브러리를 링크했는가?
- 함수 이름이 선언과 정의에서 동일한가?

예를 들어 `parse_input`이 `parse.c`에 있다면

```sh
cc main.c parse.c -o program
```

처럼 둘 다 링크 과정에 포함되어야 합니다.

### 실행 오류

실행 파일 생성에는 성공했지만 프로그램 실행 중 문제가 발생한 경우입니다.

대표적으로 다음이 있습니다.

- 예상과 다른 값을 출력함
- 잘못된 종료 상태를 반환함
- 배열 범위를 벗어남
- 잘못된 포인터를 역참조함
- 초기화되지 않은 값을 사용함
- 파일이나 메모리 할당 실패를 처리하지 않음
- 시스템 호출의 실패를 확인하지 않음
- 비정상 종료함

이 단계에서는 컴파일러가 프로그램의 의도를 대신 판단해 주지 못합니다.

따라서 입력값과 프로그램 상태를 직접 확인하고, 필요한 경우 디버거나 AddressSanitizer 같은 도구를 사용합니다.

## 오류 메시지와 종료 상태는 서로 다른 역할을 한다

다음 두 가지는 같은 정보가 아닙니다.

```sh
stderr의 오류 메시지
종료 상태
```

오류 메시지는 사람이 문제를 이해하기 위한 정보입니다.

```sh
usage: ./greet <name>
```

종료 상태는 셸이나 다른 프로그램이 성공 여부를 판단하기 위한 값입니다.

```sh
2
```

따라서 실패 상황에서는 일반적으로 둘 다 제공하는 것이 좋습니다.

```c
fprintf(stderr, "usage: %s <name>\n", argv[0]);
return 2;
```

반대로 다음과 같이 오류 메시지만 출력하고 성공 상태를 반환하면 호출자가 실패를 제대로 감지하지 못할 수 있습니다.

```c
fprintf(stderr, "입력이 잘못되었습니다.\n");
return 0;
```

## 기본 개발 습관

- 한 번에 많은 코드를 작성하기보다 작은 단위로 수정하고 자주 컴파일합니다.
- 경고가 발생하면 원인을 이해한 뒤 수정합니다.
- 경고를 없애기 위해 의미 없는 캐스트를 추가하지 않습니다.
- 정상 입력뿐 아니라 잘못된 입력과 경계값도 확인합니다.
- 함수와 시스템 호출의 실패 가능성을 확인합니다.
- 오류 메시지와 종료 상태를 함께 확인합니다.
- 새 빌드가 실패했을 때 이전 실행 파일을 잘못 실행하지 않도록 주의합니다.
- 여러 소스 파일을 사용한다면 어떤 파일이 컴파일되고 어떤 오브젝트 파일이 링크되는지 이해합니다.
- 실행 파일과 오브젝트 파일 같은 빌드 산출물은 소스 파일과 구분해서 관리합니다.

## 완료 기준

다음을 직접 수행하고 설명할 수 있어야 합니다.

1. 새 `.c` 파일을 작성하고 경고 옵션을 활성화하여 실행 파일을 만듭니다.
2. `cc` 명령에서 입력 파일, 경고 옵션, 언어 표준과 `-o` 옵션의 의미를 설명합니다.
3. 전처리, 컴파일, 어셈블과 링크가 어떤 순서로 수행되는지 설명합니다.
4. 명령행 인자 개수를 `argc`로 검사하고 필요한 값을 `argv`에서 읽습니다.
5. 셸의 따옴표 처리와 프로그램이 실제로 받는 `argv` 문자열의 차이를 설명합니다.
6. 정상 결과는 `stdout`, 오류 메시지는 `stderr`로 출력합니다.
7. 성공과 실패에 서로 다른 종료 상태를 반환하고 `$?`로 확인합니다.
8. 전처리 오류, 컴파일 오류, 링크 오류와 실행 중 오류를 구분합니다.
9. 소스를 수정했는데 실행 결과가 바뀌지 않을 때 저장, 빌드 성공 여부와 실행 파일 경로를 순서대로 확인합니다.

# 값, 분기, 반복

프로그램은 입력을 값으로 바꾸고, 조건에 따라 실행할 코드를 선택하며, 같은 작업을 여러 번 반복합니다. 이때 문법 자체보다 중요한 것은 **현재 값이 어떤 범위를 가질 수 있는지, 연산 과정에서 타입이 어떻게 변환되는지, 반복하는 동안 어떤 조건이 계속 유지되어야 하는지** 이해하는 것입니다.

## 정수 타입과 범위

```c
int count = 0;
long total = 0;
size_t length = 0;
```

- `int`: 일반적인 정수 계산, 상태값, 함수 반환값 등에 널리 사용합니다.
- `long`: 적어도 `int`와 같은 범위를 가지며, 구현에 따라 `int`보다 넓은 범위를 가질 수 있습니다.
- `size_t`: 객체의 크기와 원소 개수처럼 음수가 될 수 없는 크기 값을 나타내는 부호 없는 정수형입니다. `sizeof` 연산자의 결과 타입이기도 합니다.

C는 `int`가 반드시 32비트이고 `long`이 반드시 64비트라고 보장하지 않습니다. 타입의 실제 크기는 구현 환경에 따라 달라질 수 있습니다.

최댓값과 최솟값이 필요하면 숫자를 직접 가정하지 말고 표준 헤더가 제공하는 매크로를 사용합니다.

```c
#include <limits.h>
#include <stdint.h>
#include <stdio.h>

int main(void) {
    printf("INT_MIN  : %d\n", INT_MIN);
    printf("INT_MAX  : %d\n", INT_MAX);
    printf("LONG_MIN : %ld\n", LONG_MIN);
    printf("LONG_MAX : %ld\n", LONG_MAX);
    printf("SIZE_MAX : %zu\n", (size_t)SIZE_MAX);

    return 0;
}
```

일반적인 64비트 Linux 환경에서는 다음과 비슷한 결과가 나올 수 있습니다.

```text
INT_MIN  : -2147483648
INT_MAX  : 2147483647
LONG_MIN : -9223372036854775808
LONG_MAX : 9223372036854775807
SIZE_MAX : 18446744073709551615
```

그러나 이 값 자체를 모든 C 환경에서 동일하다고 가정해서는 안 됩니다.

`SIZE_MAX`는 `size_t`가 표현할 수 있는 최댓값입니다. `size_t` 값을 `printf`로 출력할 때는 `%zu`를 사용합니다.

## 부호 있는 값과 부호 없는 값

다음 코드는 겉으로 보면 `-1 < 10`을 비교하는 것처럼 보입니다.

```c
int index = -1;
size_t length = 10;

if (index < length) {
    puts("inside");
} else {
    puts("Index is out of bounds.");
}
```

하지만 일반적인 환경에서는 다음과 같이 출력됩니다.

```text
Index is out of bounds.
```

이유는 비교하기 전에 두 피연산자의 타입을 맞추기 위한 **암시적 형 변환(implicit conversion)** 이 발생하기 때문입니다.

`length`는 `size_t`, 즉 부호 없는 정수형입니다. 해당 환경에서 `size_t`가 `int`의 모든 값을 표현할 수 있는 더 높은 순위의 부호 없는 타입이라면 `index`도 그 타입으로 변환됩니다.

개념적으로 다음과 같은 일이 발생합니다.

```text
index
-1
↓ 부호 없는 타입으로 변환
매우 큰 양수
```

64비트 `size_t` 환경이라면 `-1`은 보통 다음과 같은 값으로 변환됩니다.

```text
18446744073709551615
```

따라서 실제 비교는 개념적으로 다음에 가까워집니다.

```text
18446744073709551615 < 10
```

결과는 거짓입니다.

중요한 것은 **부호가 다르면 항상 부호 없는 타입으로 변환된다**고 단순하게 외우는 것이 아닙니다. 실제 변환은 정수 승격과 일반 산술 변환 규칙에 의해 결정됩니다. 다만 `int`와 일반적인 64비트 `size_t`의 비교에서는 위와 같은 문제가 매우 흔합니다.

인덱스가 음수가 될 수 있는 타입이라면 음수 여부를 먼저 검사합니다.

```c
if (index >= 0 && (size_t)index < length) {
    /* 유효한 범위입니다. */
}
```

여기서는 `&&`의 짧은 평가 때문에 `index < 0`이면 오른쪽 표현식 자체를 평가하지 않습니다.

따라서 `(size_t)index` 변환은 `index`가 음수가 아님을 확인한 뒤에만 수행됩니다.

캐스트는 경고를 숨기기 위한 도구가 아닙니다.

```c
(size_t)index
```

처럼 변환하려면 먼저 원래 값이 변환 대상 타입에서 의도한 의미를 유지할 수 있는지 확인해야 합니다.

## 조건문

```c
if (value < 0) {
    fprintf(stderr, "음수는 허용하지 않습니다.\n");
    return -1;
} else if (value == 0) {
    puts("zero");
} else {
    puts("positive");
}
```

조건식은 해당 값이 무엇을 의미하는지 코드만 보고 판단할 수 있도록 작성하는 것이 좋습니다.

특히 포인터는 명시적으로 `NULL`과 비교하면 의도를 쉽게 확인할 수 있습니다.

```c
if (pointer == NULL) {
    return -1;
}
```

다음 코드도 C에서는 올바릅니다.

```c
if (!pointer) {
    return -1;
}
```

어느 형태가 더 좋은지는 프로젝트의 코딩 규칙에 따라 달라질 수 있습니다. 중요한 것은 두 표현이 포인터가 널 포인터인지 검사한다는 의미를 정확히 이해하는 것입니다.

정수나 논리 상태 역시 무조건 비교식을 길게 쓰는 것이 좋은 것은 아닙니다.

예를 들어 다음 두 조건은 의도가 다릅니다.

```c
if (count != 0)
```

```c
if (count > 0)
```

첫 번째는 음수도 참이고, 두 번째는 양수만 참입니다. 따라서 값이 가질 수 있는 범위와 조건이 의미하는 바를 먼저 판단해야 합니다.

## 논리 연산자의 짧은 평가

`&&`와 `||`는 왼쪽 피연산자를 먼저 평가하고, 그 결과만으로 전체 결과를 결정할 수 있으면 오른쪽 피연산자를 평가하지 않습니다.

이를 **단락 평가(short-circuit evaluation)** 라고 합니다.

`&&`에서는 왼쪽이 거짓이면 오른쪽을 평가하지 않습니다.

```c
if (text != NULL && text[0] != '\0') {
    /* text가 NULL이 아닐 때만 text[0]을 읽습니다. */
}
```

만약 순서를 반대로 쓰면 문제가 됩니다.

```c
if (text[0] != '\0' && text != NULL) {
    /* 위험합니다. */
}
```

`text == NULL`이어도 `text[0]`을 먼저 읽으려고 하므로 정의되지 않은 동작이 발생할 수 있습니다.

범위 검사에서도 같은 원리를 사용합니다.

```c
if (index < length && values[index] == target) {
    /* index가 유효할 때만 values[index]를 읽습니다. */
}
```

단, `index`가 부호 있는 타입이고 음수가 될 수 있다면 앞에서 본 정수 변환 문제까지 고려해야 합니다.

예를 들어 다음은 안전하지 않을 수 있습니다.

```c
int index = -1;
size_t length = 10;

if (index < length && values[index] == target) {
    /* index < length 자체가 예상대로 동작하지 않을 수 있습니다. */
}
```

이 경우에는 다음처럼 음수 여부부터 확인합니다.

```c
if (index >= 0 &&
    (size_t)index < length &&
    values[index] == target) {
    /* 안전하게 배열 원소를 읽습니다. */
}
```

`||`에서는 반대로 왼쪽이 참이면 오른쪽을 평가하지 않습니다.

```c
if (pointer == NULL || pointer->size == 0) {
    return -1;
}
```

`pointer == NULL`이면 `pointer->size`를 읽지 않습니다.

## 반복문과 유지해야 할 조건

```c
size_t index = 0;

while (index < length) {
    process(values[index]);
    ++index;
}
```

반복문은 단순히 "조건이 참인 동안 실행한다"는 문법만 보는 것보다 다음 네 가지를 확인하는 것이 중요합니다.

- 반복을 시작하기 전에 어떤 값이 준비되어 있습니까?
- 본문에 들어올 때 반드시 참이어야 하는 조건은 무엇입니까?
- 한 번 반복할 때 어떤 값이 변합니까?
- 그 변화가 결국 종료 조건으로 이어집니까?

위 반복문에서는 시작 전에 다음이 성립합니다.

```c
index == 0
```

본문에 진입할 때는 조건 검사 때문에 항상 다음이 성립합니다.

```c
index < length
```

따라서 `values`가 적어도 `length`개의 원소를 가진 유효한 배열이라는 전제 아래 다음 접근이 가능합니다.

```c
values[index]
```

본문이 끝날 때마다:

```c
++index;
```

가 실행되므로 `index`는 종료 조건인 `index >= length`에 가까워집니다.

반복문의 각 반복 전후에 계속 유지되어야 하는 성질을 **루프 불변식(loop invariant)** 이라고 부릅니다.

이 예에서는 다음과 같은 성질을 생각할 수 있습니다.

```c
0 <= index <= length
```

그리고 본문에 진입하는 순간에는:

```c
0 <= index < length
```

이므로 배열 접근이 가능합니다.

단, `size_t`는 부호 없는 타입이므로 `0 <= index`는 항상 참입니다. 실제 코드에서는 보통 별도로 검사할 필요가 없습니다.

### 종료 조건

반복문의 조건이 언젠가 거짓이 되는지도 확인해야 합니다.

다음 코드는 문제가 있습니다.

```c
size_t index = 0;

while (index < length) {
    process(values[index]);
}
```

`index`가 바뀌지 않으므로 `length > 0`이면 반복은 종료되지 않습니다.

반대로 다음 코드에서는 매번 `index`가 증가합니다.

```c
++index;
```

따라서 정상적인 범위의 `length`에 대해서는 결국 `index == length`가 되어 반복을 종료합니다.

## `for`와 `while`

초기화, 반복 조건, 갱신이 하나의 반복 변수에 집중되어 있다면 `for`문이 구조를 파악하기 쉽습니다.

```c
for (size_t index = 0; index < length; index++) {
    total += values[index];
}
```

다음 `while`문과 기본적으로 같은 구조입니다.

```c
size_t index = 0;

while (index < length) {
    total += values[index];
    index++;
}
```

반면 반복이 단순한 인덱스 증가보다 복잡한 상태 변화에 의해 종료된다면 `while`문이 더 자연스러울 수 있습니다.

```c
while ((line = read_line()) != NULL) {
    process(line);
}
```

따라서 `for`가 항상 `while`보다 좋은 것은 아닙니다. 반복을 제어하는 값과 종료 조건이 어떤 형태인지에 맞추어 선택합니다.

## 누적 상태

여러 입력을 처리하면서 통계를 계산하려면 반복 과정에서 어떤 상태를 유지해야 하는지 먼저 정합니다.

```c
struct statistics {
    size_t count;
    long minimum;
    long maximum;
    long sum;
};
```

각 필드는 다음 의미를 가질 수 있습니다.

```text
count   : 지금까지 처리한 값의 개수
minimum : 지금까지 본 값 중 최솟값
maximum : 지금까지 본 값 중 최댓값
sum     : 지금까지 본 값의 합
```

최솟값과 최댓값은 아직 입력이 하나도 없을 때 의미 있는 값이 존재하지 않습니다.

따라서 첫 번째 입력을 별도로 처리하는 방법이 자연스럽습니다.

```c
if (stats->count == 0) {
    stats->minimum = value;
    stats->maximum = value;
} else {
    if (value < stats->minimum) {
        stats->minimum = value;
    }

    if (value > stats->maximum) {
        stats->maximum = value;
    }
}
```

예를 들어 다음처럼 시작하면 문제가 생길 수 있습니다.

```c
stats->minimum = 0;
```

입력이 다음과 같다고 가정합니다.

```text
10
20
30
```

실제 최솟값은 `10`이지만 초기값 `0`보다 작은 입력은 없으므로 결과가 계속 `0`으로 남을 수 있습니다.

```text
실제 입력의 최솟값: 10
프로그램의 결과:     0
```

`0`은 실제로 입력된 적조차 없습니다.

따라서 최솟값과 최댓값에는 임의의 "적당한 값"을 넣기보다 **첫 번째 실제 입력값을 초기 기준으로 사용하는 방법**이 일반적으로 가장 단순하고 안전합니다.

다른 방법으로는 `LONG_MAX`, `LONG_MIN`을 사용할 수도 있습니다.

```c
long minimum = LONG_MAX;
long maximum = LONG_MIN;
```

하지만 이 방식도 입력이 한 번도 없었던 경우를 별도로 구분해야 합니다.

따라서 `count == 0` 같은 상태를 이미 관리하고 있다면 첫 입력으로 초기화하는 방법이 의미를 가장 직접적으로 표현합니다.

## 누적 합과 오버플로

다음 코드에는 숨은 문제가 있습니다.

```c
stats->sum += value;
```

`sum`과 `value`가 각각 유효한 `long` 값이더라도 두 값을 더한 결과가 `long`의 범위를 벗어날 수 있습니다.

따라서 누적 통계를 계산할 때는 **입력 하나의 범위뿐 아니라 누적 결과의 범위도 확인해야 합니다.**

## 오버플로는 계산 전에 검사하기

부호 있는 정수의 산술 결과가 해당 타입이 표현할 수 있는 범위를 벗어나면 **정의되지 않은 동작(undefined behavior, UB)** 이 발생합니다.

따라서 다음처럼 먼저 계산하고 검사해서는 안 됩니다.

```c
long result = left + right;

if (result > LONG_MAX) {
    /* 이미 늦었습니다. */
}
```

`left + right` 자체에서 이미 오버플로가 발생할 수 있기 때문입니다.

게다가 `result`는 `long`이므로 정상적인 C 실행에서 `LONG_MAX`보다 큰 `long` 값을 담는다는 전제 자체도 성립하지 않습니다.

덧셈은 계산 전에 검사합니다.

```c
#include <limits.h>

int add_long(long left, long right, long *out)
{
    if (out == NULL) {
        return -1;
    }

    if ((right > 0 && left > LONG_MAX - right) ||
        (right < 0 && left < LONG_MIN - right)) {
        return -1;
    }

    *out = left + right;
    return 0;
}
```

### 양수를 더하는 경우

`right > 0`이라고 가정합니다.

우리가 확인하고 싶은 것은 다음입니다.

```c
left + right <= LONG_MAX
```

하지만 위험한 `left + right`를 먼저 계산할 수는 없습니다.

따라서 식을 변형합니다.

```c
left <= LONG_MAX - right
```

즉 다음 조건이면 덧셈할 수 없습니다.

```c
left > LONG_MAX - right
```

`right > 0`이므로 `LONG_MAX - right` 자체는 `long` 범위 안에서 안전하게 계산할 수 있습니다.

### 음수를 더하는 경우

`right < 0`이면 결과가 `LONG_MIN`보다 작아질 가능성을 검사합니다.

원래 필요한 조건은 다음입니다.

```c
left + right >= LONG_MIN
```

이를 변형하면:

```c
left >= LONG_MIN - right
```

따라서 다음 조건이면 언더플로가 발생합니다.

```c
left < LONG_MIN - right
```

여기서는 `right < 0`이므로 `LONG_MIN - right`는 `LONG_MIN`에서 양의 방향으로 이동하는 계산이 되어 안전합니다.

이처럼 **검사식 자체에서 먼저 오버플로가 발생하지 않는지도 확인해야 합니다.**

## 뺄셈과 곱셈

뺄셈과 곱셈도 같은 원칙을 적용합니다.

잘못된 접근은 다음과 같습니다.

```c
long result = left * right;

if (/* result가 범위를 벗어났는지 확인 */) {
    /* 이미 곱셈이 실행되었습니다. */
}
```

위험한 연산을 먼저 수행하면 검사 자체가 의미가 없습니다.

특히 곱셈은 양수와 음수 조합에 따라 검사 조건이 여러 경우로 나뉘므로 덧셈보다 주의가 필요합니다.

핵심 원칙은 다음과 같습니다.

> 범위를 벗어날 가능성이 있는 연산은 먼저 실행하지 않고, 안전한 비교식으로 연산 가능 여부를 판단한 뒤 실행합니다.

## 부호 없는 정수의 오버플로

부호 없는 정수는 부호 있는 정수와 규칙이 다릅니다.

예를 들어:

```c
size_t value = SIZE_MAX;
value++;
```

부호 없는 정수 연산은 표현 가능한 범위를 넘어가면 `2^N`을 기준으로 순환합니다.

개념적으로:

```c
SIZE_MAX + 1
→ 0
```

이 동작 자체는 C에서 정의되어 있습니다.

하지만 **정의된 동작이라고 해서 프로그램의 의도에 맞는 것은 아닙니다.**

예를 들어 크기를 계산할 때:

```c
size_t bytes = count * sizeof(int);
```

곱셈 결과가 `size_t` 범위를 넘어 순환하면 실제보다 작은 메모리 크기가 계산될 수 있습니다.

따라서 메모리 크기, 인덱스, 개수처럼 순환을 원하지 않는 값에서는 부호 없는 정수도 계산 전에 범위를 검사해야 합니다.

## `switch`

여러 개의 정수형 값이나 열거형 값에 따라 실행할 코드를 선택할 때 `switch`를 사용할 수 있습니다.

```c
switch (command) {
case COMMAND_START:
    start();
    break;

case COMMAND_STOP:
    stop();
    break;

default:
    return -1;
}
```

`switch`는 `command`와 일치하는 `case`부터 실행을 시작합니다.

중요한 점은 `case`가 자동으로 실행을 끝내지 않는다는 것입니다.

```c
switch (value) {
case 1:
    puts("one");

case 2:
    puts("two");
    break;
}
```

`value == 1`이면 다음 두 문장이 모두 실행됩니다.

```sh
one
two
```

이를 **fallthrough**라고 합니다.

`break`를 생략한 fallthrough는 **정의되지 않은 동작이 아닙니다. C에서 정의된 정상적인 제어 흐름입니다.**

따라서 의도하지 않은 fallthrough를 막으려면 각 `case`가 독립적으로 끝나야 하는 위치에 `break`, `return` 등의 제어문을 사용합니다.

일부 코드는 fallthrough를 의도적으로 사용하기도 합니다.

```c
switch (character) {
case ' ':
case '\t':
case '\n':
    return 1;

default:
    return 0;
}
```

여기서는 `' '`, `'\t'`, `'\n'`을 모두 같은 방식으로 처리하기 위해 앞의 `case`에 `break`를 두지 않았습니다.

따라서 중요한 것은 "`case`마다 무조건 `break`를 쓴다"가 아니라 **fallthrough가 의도된 것인지 확인하는 것**입니다.

## 완료 기준

1. `int`, `long`, `size_t`의 용도가 다르며 실제 크기는 구현에 따라 달라질 수 있음을 설명합니다.
2. 부호 있는 정수와 부호 없는 정수를 비교할 때 암시적 형 변환이 결과를 바꿀 수 있는 이유를 설명합니다.
3. 음수일 수 있는 인덱스를 `size_t`와 비교하기 전에 음수 여부를 검사합니다.
4. `&&`와 `||`의 단락 평가를 이용해 포인터와 배열 접근 전에 유효성을 검사합니다.
5. 반복문에서 초기 상태, 유지 조건, 상태 변화, 종료 조건을 구분합니다.
6. 루프 불변식이 반복하는 동안 계속 유지되어야 하는 성질임을 설명합니다.
7. 최솟값과 최댓값을 임의의 `0`으로 초기화하면 잘못된 결과가 나올 수 있는 이유를 설명합니다.
8. 첫 번째 실제 입력값을 최솟값과 최댓값의 초기 기준으로 사용할 수 있습니다.
9. 부호 있는 정수 오버플로는 연산 후가 아니라 연산 전에 검사해야 하는 이유를 설명합니다.
10. 오버플로 검사식 자체도 해당 타입의 범위를 벗어나지 않아야 함을 이해합니다.
11. 부호 없는 정수의 순환은 정의된 동작이지만 크기나 개수 계산에서는 여전히 논리적 오류가 될 수 있음을 설명합니다.
12. `switch`의 `break` 누락은 UB가 아니라 fallthrough를 발생시킨다는 점을 설명합니다.
13. 의도적인 fallthrough와 실수로 발생한 fallthrough를 구분합니다.

# 입력 오류와 디버깅

문제가 발생하면 먼저 **실패의 종류**를 구분해야 합니다. 사용자가 잘못된 값을 입력한 경우와 프로그램이 잘못된 메모리에 접근한 경우는 원인도 다르고 처리 방법도 다릅니다.

특히 프로그램 내부 결함을 정상적인 입력 오류처럼 처리해서는 안 됩니다. 예를 들어 배열 범위를 벗어난 접근을 발견했는데 단순히 `"잘못된 입력입니다"`를 출력하고 계속 실행한다면, 실제 원인을 숨길 뿐입니다.

## 실패 종류

| 종류 | 예 | 처리 방법 |
| --- | --- | --- |
| 입력 형식 오류 | 인자 누락, 숫자가 아닌 문자열                         | 진단 메시지를 출력하고 프로그램이 정한 종료 상태를 반환합니다.          |
| 값 범위 오류   | 음수 금지인데 음수 입력, 허용 범위를 넘는 값          | 입력을 거부하고, 가능하면 기존 상태를 변경하지 않습니다.                |
| 자원 확보 실패 | `malloc`, `open`, `fork` 실패                         | 이미 확보한 자원을 정리하고 호출자에게 실패를 알립니다.                 |
| 코드 결함      | 배열 범위 밖 접근, 해제 후 사용, 잘못된 포인터 역참조 | 재현 조건을 만든 뒤 디버거와 sanitizer로 원인을 찾아 코드를 수정합니다. |

여기서 중요한 차이가 있습니다.

- **입력 오류**는 프로그램이 예상하고 처리해야 하는 상황입니다.
- **자원 확보 실패**도 정상적인 실행 중 발생할 수 있으므로 처리 코드가 필요합니다.
- **코드 결함**은 정상적인 실행 결과가 아닙니다. 오류 메시지를 잘 만드는 것보다 결함 자체를 제거하는 것이 우선입니다.

## `strtol`로 정수 문자열 전체 검사하기

`atoi`는 간단하지만 입력 검증에는 적합하지 않습니다.

예를 들어 다음 두 호출은 구분하기 어렵습니다.

```c
atoi("0");      /* 정상적인 0 */
atoi("hello");  /* 변환 실패지만 역시 0 반환 */
```

또한 입력 값이 `int` 범위를 벗어났을 때 신뢰할 수 있는 오류 검사 방법도 제공하지 않습니다.

정수 문자열을 검증해야 한다면 `strtol`을 사용하는 편이 적절합니다.

```c
#include <ctype.h>
#include <errno.h>
#include <stdlib.h>

int parse_long(const char *text, long *out_value) {
    char *end;
    long value;

    if (text == NULL || out_value == NULL || text[0] == '\0' ||
        isspace((unsigned char)text[0])) {
        return -1;
    }

    errno = 0;
    value = strtol(text, &end, 10);

    if (errno == ERANGE || end == text || *end != '\0') {
        return -1;
    }

    *out_value = value;
    return 0;
}
```

이 함수는 **문자열 전체가 하나의 유효한 `long` 정수 표현인지** 검사합니다.

검사 순서는 다음과 같습니다.

1. `text`와 `out_value`가 `NULL`인지 확인합니다.
2. 빈 문자열을 거부합니다.
3. 이 프로그램의 입력 규칙에서 허용하지 않는 앞 공백을 거부합니다.
4. `errno`를 `0`으로 초기화합니다.
5. `strtol`을 호출합니다.
6. `end == text`인지 확인합니다. 같다면 숫자를 한 글자도 변환하지 못한 것입니다.
7. `*end == '\0'`인지 확인합니다. 아니라면 숫자 뒤에 변환되지 않은 문자가 남아 있습니다.
8. `errno == ERANGE`인지 확인합니다. 결과가 `long`의 표현 범위를 벗어났다는 뜻입니다.
9. 모든 검사를 통과한 뒤에만 `*out_value`를 변경합니다.

예를 들어 다음과 같이 처리됩니다.

| 입력 | 결과 |
| --- | --- |
| `"123"`                 | 성공                 |
| `"-42"`                 | 성공                 |
| `"+17"`                 | 성공                 |
| `"12abc"`               | 실패                 |
| `"abc"`                 | 실패                 |
| `""`                    | 실패                 |
| `" 12"`                 | 현재 구현에서는 실패 |
| `long` 범위를 넘는 숫자 | 실패                 |

`strtol` 자체는 앞쪽 공백을 허용합니다. 따라서 `" 12"`를 허용할지 여부는 `strtol`의 문제가 아니라 **프로그램의 입력 규칙**입니다. 위 코드는 앞 공백을 허용하지 않는 규칙을 명시적으로 구현한 것입니다.

또한 `isdigit()`으로 모든 문자를 먼저 검사할 필요는 없습니다. 부호, 범위 초과, 변환 종료 위치까지 함께 처리해야 한다면 `strtol`의 결과를 검사하는 편이 더 적절합니다.

### 왜 `errno`를 먼저 `0`으로 만드는가

`errno`는 함수 호출마다 자동으로 `0`이 되는 값이 아닙니다. 이전 함수 호출에서 설정된 값이 그대로 남아 있을 수 있습니다.

따라서 다음처럼 검사하면 잘못 판단할 수 있습니다.

```c
value = strtol(text, &end, 10);

if (errno == ERANGE) {
    /* 이전 호출이 남긴 ERANGE일 수도 있습니다. */
}
```

반드시 변환 전에 초기화합니다.

```c
errno = 0;
value = strtol(text, &end, 10);
```

그리고 호출이 끝난 뒤 `ERANGE`인지 확인합니다.

### 출력 매개변수를 마지막에 변경하는 이유

다음과 같은 호출을 생각할 수 있습니다.

```c
long value = 100;

if (parse_long("invalid", &value) == -1) {
    /* value는 여전히 100 */
}
```

실패했는데 `value`가 중간 결과로 변경되어 버리면 호출자가 이전 값이 유효한지 판단하기 어려워집니다.

따라서 함수가 다음 규칙을 갖도록 만드는 것이 좋습니다.

> 성공하면 출력 값을 기록하고, 실패하면 출력 값을 변경하지 않습니다.

이러한 성질은 오류 처리와 테스트를 단순하게 만듭니다.

## 오류 메시지와 종료 상태

오류 메시지는 사용자가 문제를 수정할 수 있을 정도의 정보를 제공해야 합니다.

보통 다음 중 필요한 내용을 포함합니다.

- 어떤 입력에서 실패했는가
- 어떤 값이나 형식이 필요한가
- 필요하다면 허용 범위가 무엇인가

예:

```c
fprintf(stderr, "오류: 정수가 아닙니다: %s\n", argv[index]);
return 2;
```

여기서 `stderr`를 사용하는 이유는 정상적인 프로그램 출력인 `stdout`과 오류 진단을 분리하기 위해서입니다.

예를 들어 프로그램의 정상 출력이 다른 명령으로 전달되는 경우:

```sh
./program 10 20 > result.txt
```

오류 메시지를 `stderr`로 출력하면 정상 결과 파일에 오류 문장이 섞이지 않습니다.

종료 상태 역시 프로그램의 외부 인터페이스 일부입니다.

일반적으로:

- `0`: 성공
- `0`이 아닌 값: 실패

를 의미하지만, `1`, `2` 등의 세부 의미는 프로그램이 직접 정할 수 있습니다.

중요한 것은 **같은 종류의 실패에 일관된 종료 상태를 사용하는 것**입니다.

자동 테스트에서는 오류 메시지 전체 문장을 그대로 비교하기보다, 프로그램이 실제로 보장해야 하는 요소만 검사하는 편이 낫습니다.

예를 들어 다음처럼 메시지 전체를 고정하면:

```text
오류: 정수가 아닙니다: abc
```

단순한 문구 수정만으로 테스트가 깨질 수 있습니다.

대신 다음을 검사할 수 있습니다.

- 종료 상태가 `2`인지
- `stderr`에 `"오류:"`가 포함되는지
- 잘못된 입력 `"abc"`가 포함되는지

## 최소 재현 사례 만들기

오류를 수정하려면 먼저 **같은 오류를 반복해서 발생시킬 수 있어야 합니다.**

가능하면 다음 정보를 기록합니다.

```text
실행 명령
입력 파일 또는 인자
컴파일 옵션
stdout
stderr
종료 상태
운영체제
컴파일러와 버전
```

예:

```sh
$ ./program 10 bad 30

stdout:
없음

stderr:
오류: 정수가 아닙니다: bad

exit status:
2
```

메모리 오류라면 sanitizer 출력이나 충돌 위치도 함께 기록합니다.

그다음 재현 조건을 줄입니다.

예를 들어 원래 오류가 다음처럼 발생했다면:

```sh
./program 10 20 30 40 50 bad 60 70 80
```

다음처럼 줄여 봅니다.

```sh
./program bad
```

여전히 같은 문제가 발생한다면 나머지 입력은 원인과 관계없는 것입니다.

최소 재현 사례를 만드는 목적은 단순히 입력 길이를 줄이는 것이 아니라 **문제를 발생시키는 데 필요한 조건과 필요하지 않은 조건을 구분하는 것**입니다.

## 디버그 빌드

처음 디버깅할 때는 일반적으로 다음과 같이 빌드할 수 있습니다.

```sh
cc -std=c11 -Wall -Wextra -Wpedantic -g -O0 source.c -o program
```

- `-g`: 실행 파일에 디버깅 정보를 포함합니다. 디버거가 소스 파일, 줄 번호, 변수 정보를 표시할 수 있게 합니다.
- `-O0`: 최적화를 비활성화합니다. 처음 조사할 때 소스 코드와 실제 실행을 대응시키기 쉬워집니다.

최적화가 활성화되면 컴파일러가 코드를 재배치하거나 제거할 수 있습니다.

예를 들어:

- 변수가 실제 메모리에 존재하지 않을 수 있습니다.
- 코드 실행 순서가 소스 순서와 달라 보일 수 있습니다.
- 일부 함수가 인라인 처리될 수 있습니다.

따라서 처음에는 `-O0`가 편리합니다.

하지만 수정이 끝난 뒤에는 실제 사용할 최적화 설정에서도 다시 검사해야 합니다.

```sh
cc -std=c11 -Wall -Wextra -Wpedantic -O2 source.c -o program
```

`-O0`에서만 정상이라고 해서 결함이 사라진 것은 아닙니다. 정의되지 않은 동작이 있는 프로그램은 최적화 수준에 따라 증상이 달라질 수 있습니다.

## 디버거 기본 사용

GDB 예시:

```sh
gdb ./program

(gdb) break main
(gdb) run 10 bad 30
(gdb) next
(gdb) step
(gdb) print index
(gdb) backtrace
```

LLDB 예시:

```sh
lldb ./program

(lldb) breakpoint set --name main
(lldb) run 10 bad 30
(lldb) next
(lldb) step
(lldb) frame variable index
(lldb) bt
```

주요 명령의 역할은 다음과 같습니다.

| 목적 | GDB | LLDB |
| --- | --- | --- |
| 중단점 설정                 | `break main`  | `breakpoint set --name main` |
| 실행                        | `run`         | `run`                        |
| 현재 함수에서 다음 줄 실행  | `next`        | `next`                       |
| 호출되는 함수 안으로 들어감 | `step`        | `step`                       |
| 변수 확인                   | `print index` | `frame variable index`       |
| 호출 스택 확인              | `backtrace`   | `bt`                         |

`next`와 `step`의 차이는 특히 중요합니다.

다음 코드에서:

```c
value = parse_long(argv[1], &number);
```

`next`는 `parse_long` 호출 전체를 실행하고 다음 줄로 이동합니다.

`step`은 `parse_long` 함수 내부로 들어갑니다.

디버깅할 때 코드를 처음부터 끝까지 무작정 한 줄씩 실행하는 방식은 비효율적입니다.

먼저 가설을 세우는 편이 좋습니다.

예:

> `index`가 배열 길이보다 커진 뒤에도 반복문이 한 번 더 실행되는 것 같다.

그러면 해당 지점 근처에 중단점을 두고 다음을 확인합니다.

```text
index는 얼마인가?
length는 얼마인가?
반복 조건은 무엇인가?
호출자가 어떤 값을 전달했는가?
```

디버거는 코드를 대신 분석하는 도구가 아니라 **가설을 실제 실행 상태와 비교하는 도구**로 사용하는 편이 좋습니다.

## AddressSanitizer와 UndefinedBehaviorSanitizer

```sh
cc -std=c11 -Wall -Wextra -Wpedantic -g \
    -fsanitize=address,undefined -fno-omit-frame-pointer \
    source.c -o program
```

### AddressSanitizer

AddressSanitizer(ASan)는 주로 메모리 접근 오류를 찾습니다.

대표적으로:

- 힙 버퍼 범위 밖 접근
- 스택 버퍼 범위 밖 접근
- 해제한 메모리 사용(use-after-free)
- 일부 중복 해제
- 일부 메모리 수명 관련 오류

예:

```c
int values[3] = {1, 2, 3};

printf("%d\n", values[3]);
```

유효한 인덱스는 `0`, `1`, `2`뿐이므로 `values[3]`은 범위를 벗어납니다.

### UndefinedBehaviorSanitizer

UndefinedBehaviorSanitizer(UBSan)는 C에서 정의되지 않은 동작 중 일부를 실행 중 검사합니다.

대표적으로:

- 부호 있는 정수 overflow
- 0으로 나누기
- 일부 잘못된 시프트 연산
- 잘못된 정렬의 포인터 접근
- 표현할 수 없는 일부 변환이나 연산

예:

```c
int value = INT_MAX;

value += 1;
```

부호 있는 정수의 표현 범위를 넘는 연산은 C에서 정의되지 않은 동작입니다.

### sanitizer의 한계

sanitizer는 **실제로 실행된 코드만 검사할 수 있습니다.**

예를 들어 다음 분기가 한 번도 실행되지 않았다면:

```c
if (rare_condition) {
    /* 이 안에 메모리 오류가 있어도 실행하지 않으면 발견되지 않을 수 있습니다. */
}
```

sanitizer를 활성화했다는 사실만으로 이 코드가 안전하다고 결론 내릴 수 없습니다.

따라서 sanitizer는 테스트를 대신하는 것이 아니라 테스트와 함께 사용해야 합니다.

또한 모든 C의 정의되지 않은 동작을 sanitizer가 검출할 수 있는 것도 아닙니다.

## 경고를 오류로 다루기

```sh
cc -std=c11 -Wall -Wextra -Wpedantic -Werror source.c -o program
```

`-Werror`는 컴파일러 경고를 컴파일 오류로 취급합니다.

이 설정의 목적은 경고를 보이지 않게 만드는 것이 아니라 **경고의 원인을 제거하도록 강제하는 것**입니다.

따라서 다음과 같은 방식은 주의해야 합니다.

```c
if ((size_t)index < length) {
```

컴파일러가 signed/unsigned 비교를 경고했다고 해서 무조건 캐스트를 추가하면 경고만 사라질 수 있습니다.

예를 들어:

```c
int index = -1;
size_t length = 10;
```

여기서 `index`를 `size_t`로 변환하면 매우 큰 양수가 될 수 있습니다.

따라서 먼저 다음을 확인합니다.

- 타입 자체를 잘못 선택한 것은 아닌가?
- signed와 unsigned 값을 섞을 필요가 있는가?
- 음수가 의미 있는 값인가?
- 형식 지정자와 실제 인자의 타입이 일치하는가?
- 함수의 반환값을 확인해야 하는데 무시한 것은 아닌가?
- 변환하려는 값이 대상 타입의 표현 범위 안에 있는가?

캐스트는 타입 변환을 명시할 뿐이며, 잘못된 값이나 잘못된 설계를 자동으로 올바르게 만들지 않습니다.

## 테스트할 입력 나누기

테스트 입력은 최소한 다음 세 종류로 나누어 생각할 수 있습니다.

### 정상 사례

프로그램이 지원한다고 명시한 일반적인 입력입니다.

예:

```text
10
42
-5
```

단, 음수 지원 여부는 프로그램 규칙에 따라 달라집니다.

### 경계 사례

허용 범위의 끝이나 특별한 처리가 필요한 입력입니다.

예:

- 빈 문자열
- 한 글자 입력
- `LONG_MIN`
- `LONG_MAX`
- 길이가 정확히 버퍼 크기와 같은 입력
- 요소가 0개인 경우
- 요소가 1개인 경우

경계 사례는 단순히 "이상한 입력"이 아니라 **조건식의 경계에서 동작이 바뀌는 입력**입니다.

예를 들어:

```c
if (length < capacity)
```

를 검사한다면 다음 값들이 중요합니다.

```text
length == capacity - 1
length == capacity
length == capacity + 1
```

### 실패 사례

프로그램이 명시적으로 거부하거나 시스템 오류로 처리해야 하는 경우입니다.

예:

- 숫자가 아닌 문자열
- 허용 범위를 넘는 숫자
- 잘못된 파일 경로
- `malloc` 실패
- `open` 실패
- `fork` 실패

할당 실패나 시스템 호출 실패는 실제 환경에서 재현하기 어려울 수 있으므로, 테스트에서는 실패를 주입할 수 있는 구조를 별도로 사용하는 경우도 있습니다.

## 성공 결과만 검사하지 않기

다음 함수가 있다고 가정합니다.

```c
int parse_long(const char *text, long *out_value);
```

성공 테스트만 하면 다음만 확인하게 됩니다.

```c
long value;

assert(parse_long("42", &value) == 0);
assert(value == 42);
```

실패 동작도 검사해야 합니다.

```c
long value = 123;

assert(parse_long("abc", &value) == -1);
assert(value == 123);
```

두 번째 검사는 함수가 실패했을 때 출력 매개변수를 변경하지 않는다는 규칙을 확인합니다.

상태를 가진 객체에서도 같은 원칙을 적용할 수 있습니다.

예를 들어 배열에 값을 추가하는 함수가 메모리 할당에 실패했다면 다음을 확인할 수 있습니다.

```text
함수가 실패를 반환했는가?
기존 요소 수는 유지되었는가?
기존 요소의 내용은 유지되었는가?
메모리 누수가 발생하지 않았는가?
```

즉 테스트는 단순히 **원하는 결과가 나오는지**뿐 아니라 **실패 후 프로그램이 어떤 상태에 남는지**까지 확인해야 합니다.

## 완료 기준

이 내용을 학습했다면 다음을 설명하고 직접 확인할 수 있어야 합니다.

1. 입력 오류, 자원 확보 실패, 코드 결함의 차이를 설명할 수 있습니다.
2. `atoi`보다 `strtol`이 입력 검증에 적합한 이유를 설명할 수 있습니다.
3. `strtol` 결과를 `errno`, `end == text`, `*end == '\0'`으로 검사할 수 있습니다.
4. `errno`를 변환 전에 초기화해야 하는 이유를 설명할 수 있습니다.
5. 함수 실패 시 출력 매개변수를 변경하지 않도록 구현할 수 있습니다.
6. 오류를 반복해서 발생시키는 최소 재현 사례를 만들 수 있습니다.
7. GDB 또는 LLDB에서 중단점, 변수 값, 호출 스택을 확인할 수 있습니다.
8. `next`와 `step`의 차이를 설명할 수 있습니다.
9. ASan과 UBSan이 주로 어떤 종류의 오류를 찾는지 구분할 수 있습니다.
10. sanitizer가 실행되지 않은 코드의 안전성을 보장하지 않는다는 점을 이해합니다.
11. 컴파일러 경고를 단순한 캐스트로 숨기기 전에 타입과 연산의 의미를 확인합니다.
12. 정상 사례, 경계 사례, 실패 사례를 구분해 테스트할 수 있습니다.
13. 실패 후 출력 값과 기존 프로그램 상태가 유지되는지도 테스트할 수 있습니다.

# C 프로그램의 구성과 전처리

C 프로그램은 소스 파일에서 곧바로 실행 파일이 만들어지는 방식이 아닙니다. 각 `.c` 파일은 전처리를 거쳐 하나의 **번역 단위(translation unit)** 가 되고, 번역 단위마다 독립적으로 컴파일됩니다. 이후 생성된 여러 오브젝트 파일을 링크하여 실행 파일이나 라이브러리를 만듭니다.

## 빌드 단계

```text
.c 파일 + 포함한 헤더
  ↓ 전처리
번역 단위
  ↓ 컴파일
어셈블리 코드
  ↓ 어셈블
오브젝트 파일(.o)
  ↓ 링크
실행 파일 또는 라이브러리
```

실제로 `cc`를 사용하면 위 도구들을 직접 하나씩 실행할 필요는 없습니다. `cc`는 전처리기, 컴파일러, 어셈블러, 링커를 필요한 순서로 호출하는 **컴파일러 드라이버**입니다.

```sh
cc -std=c11 -Wall -Wextra -Wpedantic main.c text.c -o textstat
```

이 명령 하나로 `main.c`와 `text.c`를 각각 처리한 뒤 필요한 오브젝트 파일을 링크하여 `textstat` 실행 파일을 만듭니다.

문제가 생겼을 때는 전처리, 컴파일, 어셈블, 링크, 실행 중 어느 단계에서 실패했는지 구분할 수 있어야 합니다. 예를 들어 문법이나 타입 문제는 주로 컴파일 단계에서 발견되고, 선언한 함수의 정의를 찾지 못하는 문제는 주로 링크 단계에서 발견됩니다.

## 각 단계의 결과 확인하기

```sh
cc -std=c11 -E main.c -o main.i
cc -std=c11 -S main.c -o main.s
cc -std=c11 -c main.c -o main.o
cc main.o text.o -o textstat
```

* `-E`: 전처리까지만 수행하고 결과를 만듭니다.
* `-S`: 전처리와 컴파일을 수행하여 어셈블리 소스를 만듭니다.
* `-c`: 전처리, 컴파일, 어셈블을 수행하여 오브젝트 파일을 만들고 링크는 하지 않습니다.
* 마지막 명령: 이미 만들어진 오브젝트 파일을 링크합니다.

단계별 결과는 개념적으로 다음과 같이 이어집니다.

```text
main.c
  ↓
main.i
  ↓
main.s
  ↓
main.o
  ↓
실행 파일
```

이 중간 결과를 확인하면 문제가 어느 단계에서 생겼는지 좁혀 갈 수 있습니다.

## 전처리기는 토큰을 바꿉니다

전처리기는 C 타입을 검사하거나 함수를 실행하는 단계가 아닙니다. `#include`, `#define`, `#if` 같은 전처리 지시문을 처리하고 매크로를 확장하여 이후 컴파일러가 읽을 토큰열을 만듭니다.

예를 들어 `#include`는 지정한 헤더의 내용을 현재 소스에 포함시키고, `#define`으로 정의한 매크로는 사용 위치에서 치환됩니다.

### 객체형 매크로

```c
#define BUFFER_SIZE 4096
#define DEBUG_ENABLED 1
```

전처리 과정에서 매크로 이름은 지정된 **치환 목록(replacement list)** 으로 바뀝니다.

```c
char buffer[BUFFER_SIZE];
```

는 개념적으로 다음과 같이 바뀝니다.

```c
char buffer[4096];
```

매크로 자체에는 C 타입이 없습니다. 따라서 타입이 있는 상수가 필요한 경우에는 상황에 따라 `enum` 상수나 `const` 객체가 더 알맞을 수 있습니다.

```c
enum {
    BUFFER_SIZE = 4096
};
```

다만 매크로, `enum`, `const` 객체는 완전히 같은 기능이 아닙니다. 전처리 단계에서 값이 필요한지, 실제 타입과 저장 공간이 필요한지에 따라 적절한 방법을 선택해야 합니다.

### 함수형 매크로

```c
#define MIN(a, b) ((a) < (b) ? (a) : (b))
```

함수 호출처럼 보이지만 실제 함수가 아닙니다. 전달한 인자는 매크로 본문의 해당 위치에 토큰 형태로 들어갑니다.

따라서 인자가 한 번만 평가된다는 보장이 없습니다.

```c
MIN(index++, limit)
```

위 호출은 개념적으로 다음과 비슷하게 확장될 수 있습니다.

```c
((index++) < (limit) ? (index++) : (limit))
```

`MIN`의 본문에서 `a`를 두 번 사용하므로 조건이 참이면 `index++`도 두 번 평가됩니다. 따라서 `++`, `--`, 대입, 함수 호출처럼 부수 효과가 있는 표현식은 함수형 매크로의 인자로 전달하지 않는 편이 안전합니다.

괄호도 중요합니다.

```c
#define SQUARE_BAD(x) x * x
#define SQUARE(x) ((x) * (x))
```

예를 들어:

```c
SQUARE_BAD(1 + 2)
```

는 다음과 같이 확장됩니다.

```c
1 + 2 * 1 + 2
```

연산자 우선순위 때문에 기대한 `9`가 나오지 않습니다.

반면:

```c
SQUARE(1 + 2)
```

는 다음과 같이 확장됩니다.

```c
((1 + 2) * (1 + 2))
```

따라서 함수형 매크로에서는 일반적으로 각 인자와 전체 결과를 괄호로 감쌉니다. 단, 괄호를 넣어도 **인자의 중복 평가 문제는 해결되지 않습니다.**

### 여러 줄 매크로

치환 목록을 여러 줄에 걸쳐 작성하려면 각 줄 끝에 `\`를 둬서 다음 줄까지 같은 매크로 정의가 이어진다는 것을 표시합니다.

```c
#define CHECK(expression)                                      \
    do {                                                       \
        if (!(expression)) {                                   \
            fprintf(stderr, "%s:%d: 실패: %s\n",               \
                    __FILE__, __LINE__, #expression);           \
            return 1;                                          \
        }                                                      \
    } while (0)
```

`do { ... } while (0)`은 여러 문장을 가진 매크로를 호출 위치에서 **하나의 문장처럼 사용할 수 있게 하는 관용구**입니다.

예를 들어 다음과 같이 사용할 수 있습니다.

```c
if (ready)
    CHECK(value > 0);
else
    recover();
```

단순한 `{ ... }` 블록만 치환하면 호출부의 세미콜론이나 `if`/`else`의 결합 때문에 예상하지 못한 문법 문제가 생길 수 있습니다. `do { ... } while (0)`을 사용하면 일반 함수 호출처럼 매크로 호출 뒤에 세미콜론을 붙이는 형태를 유지할 수 있습니다.

### 문자열화 연산자 `#`

함수형 매크로의 치환 목록에서 `#parameter`를 사용하면 호출 시 전달된 토큰을 문자열 리터럴로 만들 수 있습니다.

```c
#define STRINGIFY(value) #value

STRINGIFY(buffer_size)
/* "buffer_size" */
```

이를 **문자열화(stringification)** 라고 합니다.

다음처럼 테스트나 진단 코드에서 실패한 표현식 자체를 출력할 때 유용합니다.

```c
#define CHECK(expression) \
    fprintf(stderr, "failed: %s\n", #expression)
```

```c
CHECK(value > 0);
```

출력 예:

```text
failed: value > 0
```

### 미리 정의된 매크로

C 구현은 여러 미리 정의된 매크로를 제공합니다. 그중 자주 사용하는 것이 다음 두 개입니다.

```c
__FILE__
__LINE__
```

`__FILE__`은 현재 소스 파일 이름을 나타내는 문자열 리터럴로 확장됩니다.

`__LINE__`은 현재 소스의 줄 번호를 나타내는 정수 상수로 확장됩니다.

```c
fprintf(stderr,
        "%s:%d: 잘못된 상태\n",
        __FILE__,
        __LINE__);
```

진단 메시지나 테스트 실패 위치를 출력할 때 유용합니다.

### 가변 인자 매크로

C99부터 함수형 매크로도 가변 개수의 인자를 받을 수 있습니다.

```c
#define LOG(format, ...) \
    fprintf(stderr, format, __VA_ARGS__)
```

예를 들어:

```c
LOG("value = %d\n", value);
```

에서 `...`에 전달된 토큰들이 `__VA_ARGS__` 위치에 들어갑니다.

매크로의 `...`와 `<stdarg.h>`를 사용하는 가변 인자 함수는 서로 다른 기능입니다.

```c
int log_message(const char *format, ...);
```

가변 인자 매크로는 **전처리 과정에서 토큰을 치환**합니다. 반면 `va_list`, `va_start`, `va_arg`, `va_end`는 **실제 함수 호출로 전달된 인자 값을 함수 내부에서 읽기 위해 사용**합니다.

가변 인자가 비어 있는 다음과 같은 호출:

```c
LOG("done\n");
```

까지 지원하려면 사용하는 C 표준과 컴파일러 기능에 따라 작성 방법이 달라질 수 있습니다. 특히 C11 수준의 이식성이 중요한 코드라면 가변 인자를 하나 이상 요구하거나 인자가 없는 경우를 위한 별도 매크로를 두는 방법이 단순합니다.

### 조건부 컴파일

```c
#ifdef DEBUG
fprintf(stderr, "debug mode\n");
#endif
```

`#ifdef DEBUG`는 `DEBUG`라는 매크로가 **정의되어 있는지** 확인합니다. 값이 `0`인지 `1`인지를 검사하는 것이 아닙니다.

예를 들어:

```c
#define DEBUG 0
```

이어도:

```c
#ifdef DEBUG
```

의 조건은 참입니다.

값을 조건으로 사용하려면 다음처럼 작성할 수 있습니다.

```c
#if DEBUG
```

같은 정의 여부 검사는 `defined`를 사용해서도 표현할 수 있습니다.

```c
#if defined(DEBUG)
fprintf(stderr, "debug mode\n");
#endif
```

플랫폼이나 선택 기능에 따라 서로 다른 코드를 포함할 수도 있습니다.

```c
#if defined(__linux__)

    /* Linux에서 사용할 코드 */

#elif defined(__APPLE__)

    /* macOS에서 사용할 코드 */

#else

    /* 공통 구현 */

#endif
```

컴파일 명령의 `-D` 옵션으로 매크로를 정의할 수도 있습니다.

```sh
cc -DDEBUG source.c -o program
```

일반적인 `cc` 구현에서는 `-DDEBUG`가 `DEBUG`를 값 `1`로 정의한 것처럼 동작합니다.

값을 직접 지정할 수도 있습니다.

```sh
cc -DLOG_LEVEL=2 source.c -o program
```

Makefile에서는 전처리기 관련 옵션을 보통 `CPPFLAGS`에 둡니다.

```make
CPPFLAGS += -DDEBUG
```

### Include guard

하나의 헤더가 같은 번역 단위에 여러 경로로 포함될 수 있습니다.

```text
main.c
├── text.h
└── parser.h
    └── text.h
```

이 경우 `text.h`의 내용이 두 번 포함될 수 있습니다.

Include guard는 같은 번역 단위에서 헤더의 내용을 한 번만 처리하도록 막습니다.

```c
#ifndef OWNED_STRING_H
#define OWNED_STRING_H

/* declarations */

#endif
```

처음 포함할 때는 `OWNED_STRING_H`가 정의되어 있지 않으므로 내부 내용을 처리하고, 그 과정에서 `OWNED_STRING_H`를 정의합니다.

같은 번역 단위에서 헤더가 다시 포함되면 이미 매크로가 정의되어 있으므로 내부 내용을 다시 처리하지 않습니다.

### 토큰 결합 연산자 `##`

`##`는 두 preprocessing token을 하나의 토큰으로 결합합니다.

```c
#define MAKE_NAME(prefix, name) prefix##name

MAKE_NAME(test_, append)
/* test_append */
```

위 호출에서는 `test_`와 `append`가 결합되어 하나의 식별자인 `test_append`가 됩니다.

일반적인 응용 코드에서 자주 필요하지는 않지만 테스트 도구, 반복 선언, 코드 생성형 매크로를 읽을 때 의미를 알아둘 필요가 있습니다.

## 번역 단위

전처리를 마친 `.c` 파일 하나는 독립적으로 컴파일되는 **번역 단위**가 됩니다.

```text
main.c + main.c에서 포함한 헤더 → 번역 단위 A
text.c + text.c에서 포함한 헤더 → 번역 단위 B
```

중요한 점은 A와 B가 **서로 따로 컴파일된다는 것**입니다.

A를 컴파일할 때 컴파일러가 B의 함수 본문을 자동으로 읽는 것은 아닙니다.

예를 들어 `main.c`에서 다음 함수를 호출한다고 가정합니다.

```c
size_t length = text_length(text);
```

컴파일러가 이 호출의 타입을 검사하려면 최소한 함수 선언을 알고 있어야 합니다.

```c
size_t text_length(const char *text);
```

실제 함수 본문은 다른 번역 단위에 있어도 됩니다.

```c
/* text.c */

size_t text_length(const char *text)
{
    /* ... */
}
```

따라서 다음 두 시점을 구분해야 합니다.

```text
컴파일 시점
→ 함수의 선언을 통해 이름과 타입을 알 수 있어야 함

링크 시점
→ 실제 함수 정의를 찾을 수 있어야 함
```

## 선언과 정의

선언은 컴파일러에게 이름과 타입 등의 정보를 알려 줍니다.

```c
size_t text_length(const char *text);
extern unsigned long processed_count;
```

정의는 실제 함수 본문을 제공하거나 객체의 저장 공간을 마련합니다.

```c
size_t text_length(const char *text)
{
    /* ... */
}

unsigned long processed_count = 0;
```

함수 선언만 있고 최종 링크 대상에 함수 정의가 없으면 다음과 같은 링크 오류가 발생할 수 있습니다.

```text
undefined reference to `text_length`
```

반대로 외부 링키지를 가진 동일한 함수나 객체가 여러 곳에 정의되어 있으면 다음과 같은 오류가 발생할 수 있습니다.

```text
multiple definition of `processed_count`
```

따라서 일반적으로 헤더에는 선언을 두고, 실제 정의는 하나의 `.c` 파일에 둡니다.

## 헤더 작성

```c
#ifndef TEXT_H
#define TEXT_H

#include <stddef.h>

size_t text_length(const char *text);
size_t text_word_count(const char *text);

#endif
```

헤더 작성 시 다음을 지킵니다.

* 헤더에서 사용하는 타입에 필요한 표준 헤더를 직접 포함합니다.
* Include guard를 둡니다.
* 호출자가 알아야 하는 선언만 공개합니다.
* 일반 함수의 구현을 헤더에 넣지 않습니다.
* 변경 가능한 전역 객체의 정의를 헤더에 넣지 않습니다.
* 구현 파일도 자신의 공개 헤더를 포함하여 선언과 정의가 일치하는지 컴파일러가 검사할 수 있게 합니다.

예를 들어 다음처럼 헤더에 전역 객체를 정의하면 안 됩니다.

```c
/* text.h */

unsigned long processed_count = 0;
```

이 헤더를 여러 `.c` 파일에서 포함하면 동일한 외부 객체의 정의가 여러 번 생길 수 있습니다.

대신 헤더에는 선언만 둡니다.

```c
/* text.h */

extern unsigned long processed_count;
```

실제 정의는 하나의 `.c` 파일에 둡니다.

```c
/* text.c */

unsigned long processed_count = 0;
```

구현 파일도 자신의 공개 헤더를 포함합니다.

```c
/* text.c */

#include "text.h"
```

이렇게 하면 헤더의 선언과 구현의 정의가 서로 다른 타입을 사용했을 때 컴파일러가 문제를 발견하기 쉬워집니다.

## 내부 링키지

**링키지(linkage)** 는 같은 이름이 여러 선언에 등장했을 때 그 선언들이 **같은 함수나 객체를 가리키는지**를 설명하는 개념입니다.

예를 들어 다음 두 선언은 서로 다른 번역 단위에 있지만 같은 객체를 가리킬 수 있습니다.

```c
/* counter.c */

unsigned long processed_count = 0;
```

```c
/* main.c */

extern unsigned long processed_count;
```

이 경우 `processed_count`는 **외부 링키지(external linkage)** 를 가집니다.

반대로 파일 범위의 함수나 객체에 `static`을 붙이면 해당 이름은 **내부 링키지(internal linkage)** 를 가집니다.

```c
static int is_separator(char value)
{
    return value == ' ' ||
           value == '\t' ||
           value == '\n';
}
```

이 이름은 현재 번역 단위 안에서만 같은 함수와 연결됩니다.

따라서 서로 다른 `.c` 파일에 다음처럼 같은 이름을 정의해도 서로 다른 함수입니다.

```text
text.c
    static int is_separator(...)

parser.c
    static int is_separator(...)
```

파일 내부에서만 사용하는 보조 함수나 전역 객체는 `static`으로 두면 다른 번역 단위에 불필요하게 공개되지 않습니다.

다만 `static`의 의미는 사용 위치에 따라 달라집니다.

```c
void function(void)
{
    static int count = 0;
}
```

이 `count`는 함수 블록 내부에서만 이름을 사용할 수 있지만 객체 자체는 함수 호출이 끝나도 사라지지 않고 프로그램이 끝날 때까지 유지됩니다.

즉 파일 범위의 `static`은 주로 **내부 링키지**와 관련되고, 블록 내부의 `static`은 객체의 **저장 기간**과 관련됩니다.

## 스코프·링키지·저장 기간

세 개념은 서로 비슷해 보이지만 다른 질문에 답합니다.

| 개념    | 확인할 질문                                |
| ----- | ------------------------------------- |
| 스코프   | 이 이름을 소스의 어디에서 사용할 수 있습니까?            |
| 링키지   | 서로 다른 선언에 등장한 같은 이름이 같은 함수나 객체를 뜻합니까? |
| 저장 기간 | 객체의 저장 공간은 언제 만들어지고 언제까지 유지됩니까?       |

예를 들어:

```c
void function(void)
{
    static int count = 0;
    count++;
}
```

`count`는 다음 특성을 가집니다.

* 스코프: `function` 블록 내부
* 링키지: 없음
* 저장 기간: 정적 저장 기간

따라서 함수 밖에서는 `count`라는 이름을 사용할 수 없지만, 객체의 값은 함수 호출이 끝난 뒤에도 유지됩니다.

```c
function();
function();
function();
```

세 번 호출하면 매번 새 `count`가 생기는 것이 아니라 같은 객체가 계속 사용됩니다.

즉 **이름을 사용할 수 있는 범위**, **다른 선언과 같은 대상을 가리키는지 여부**, **객체가 존재하는 시간**은 서로 다른 개념입니다.

## 오브젝트 파일과 심볼 확인

Unix 계열 환경에서는 `nm`과 `ar`을 사용해 오브젝트 파일이나 정적 라이브러리의 내용을 확인할 수 있습니다.

```sh
nm main.o
nm text.o

ar t libtext.a
nm libtext.a
```

이를 통해 다음을 확인할 수 있습니다.

* 현재 오브젝트 파일이 정의한 심볼
* 현재 오브젝트 파일에서는 사용하지만 다른 곳에서 정의되어야 하는 심볼
* 정적 라이브러리에 실제로 포함된 오브젝트 파일
* 필요한 함수나 객체의 정의가 라이브러리에 존재하는지

여기서 **심볼(symbol)** 은 링커가 함수나 전역 객체 등을 식별하는 데 사용하는 이름이라고 이해하면 됩니다.

중요한 점은 헤더에 선언이 존재한다고 해서 실제 정의가 링크 대상에 포함되어 있다는 뜻은 아니라는 것입니다.

예를 들어:

```c
/* text.h */

size_t text_length(const char *text);
```

가 정상적으로 존재하더라도 `text_length`를 정의한 `text.o`를 링크하지 않으면:

```sh
cc main.o -o program
```

링커는 실제 함수 정의를 찾지 못합니다.

## 매크로를 읽을 때 확인할 사항

* 확장된 식의 연산자 우선순위가 의도대로 유지됩니까?
* 같은 인자가 매크로 본문에서 여러 번 사용됩니까?
* 부수 효과가 있는 표현식을 전달하면 여러 번 평가될 수 있습니까?
* 여러 문장을 가진 매크로가 하나의 문장처럼 안전하게 동작합니까?
* `#`는 어떤 토큰을 문자열로 만듭니까?
* `##`는 어떤 토큰들을 결합하여 새로운 토큰을 만듭니까?
* 어떤 `-D` 옵션이 `#if`, `#ifdef`와 연결됩니까?
* 실제 함수나 타입이 있는 상수를 사용하는 것보다 매크로가 적합한 이유가 있습니까?

## 완료 기준

1. 전처리, 컴파일, 어셈블, 링크를 구분합니다.
2. `.c` 파일마다 독립적인 번역 단위가 만들어지는 이유를 설명합니다.
3. 컴파일 시 필요한 선언과 링크 시 필요한 정의를 구분합니다.
4. 선언과 정의를 헤더와 `.c` 파일에 적절하게 나눕니다.
5. 함수형 매크로에서 인자가 중복 평가될 수 있는 이유를 설명합니다.
6. 매크로 인자와 전체 결과에 괄호가 필요한 이유를 설명합니다.
7. `#`, `##`, `__FILE__`, `__LINE__`, `__VA_ARGS__`의 용도를 구분합니다.
8. `#if`, `#ifdef`, `defined`, `-D`의 관계를 설명합니다.
9. Include guard가 같은 헤더의 중복 처리를 막는 원리를 설명합니다.
10. 스코프, 링키지, 저장 기간의 차이를 설명합니다.
11. 외부 링키지와 내부 링키지의 차이를 예제로 설명합니다.
12. 파일 범위의 `static`과 블록 내부의 `static`이 서로 다른 효과를 갖는 이유를 설명합니다.

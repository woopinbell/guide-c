# 메모리, 포인터, 문자열

C에서 포인터를 안전하게 사용하려면 포인터에 저장된 주소 값만 보면 안 됩니다. 포인터를 역참조하거나 연산하기 전에 최소한 다음을 함께 생각해야 합니다.

* 어떤 객체 또는 배열을 가리키는가
* 그 객체의 수명이 아직 끝나지 않았는가
* 해당 위치를 읽거나 쓸 권한이 있는가
* 몇 개의 원소 또는 몇 바이트까지 접근할 수 있는가
* 같은 메모리를 가리키는 다른 포인터가 존재하는가
* 동적 할당된 메모리라면 누가 해제하는가

`NULL` 검사는 이 조건 중 하나만 확인할 뿐입니다.

## 객체와 주소

```c
int value = 42;
int *pointer = &value;

*pointer = 7;
```

`&value`는 `value`의 주소를 구하고, `pointer`는 그 주소를 저장합니다.

`*pointer`는 `pointer`가 가리키는 객체에 접근합니다.

따라서:

```c
*pointer = 7;
```

은 `pointer` 자체를 바꾸는 것이 아니라 `pointer`가 가리키는 `value`에 `7`을 저장합니다.

결과적으로:

```c
value == 7
```

이 됩니다.

포인터 변수와 포인터가 가리키는 객체를 구분해야 합니다.

```text
pointer
    │
    └──→ value
          42 → 7
```

## 유효한 포인터

다음 함수는 `NULL` 포인터를 거부합니다.

```c
int read_value(const int *pointer, int *out_value)
{
    if (pointer == NULL || out_value == NULL) {
        return -1;
    }

    *out_value = *pointer;
    return 0;
}
```

하지만 `pointer != NULL`이라는 사실만으로 다음 역참조가 안전하다고 결론 내릴 수는 없습니다.

```c
*pointer
```

예를 들어 다음 포인터들은 모두 `NULL`이 아닐 수 있지만 역참조하면 안 됩니다.

* 수명이 끝난 지역 객체를 가리키는 포인터
* 이미 `free`한 메모리를 가리키는 포인터
* `realloc`으로 이동되기 전의 옛 주소
* 배열 범위를 벗어난 위치를 가리키는 포인터
* 초기화되지 않은 포인터

따라서 포인터의 유효성은 단순히 주소 값이 0인지 여부가 아니라 **가리키는 객체와 그 객체의 현재 상태**에 따라 결정됩니다.

## 저장 기간과 객체의 수명

C에서는 객체가 언제 존재하기 시작하고 언제까지 존재하는지를 구분해야 합니다.

### 자동 저장 기간

일반적인 지역 변수는 자동 저장 기간을 가집니다.

```c
int *wrong(void)
{
    int value = 42;

    return &value;
}
```

`value`의 수명은 `wrong`의 실행이 끝날 때 끝납니다.

따라서 반환된 주소 값이 그대로 남아 있더라도 그 주소를 통해 더 이상 `value`에 접근할 수 없습니다.

```c
int *pointer = wrong();
printf("%d\n", *pointer); /* 정의되지 않은 동작 */
```

이런 포인터를 흔히 **댕글링 포인터(dangling pointer)** 라고 부릅니다.

중요한 점은 포인터 변수 자체가 사라진 것이 아니라 **포인터가 가리키던 객체의 수명이 끝났다는 것**입니다.

### 정적 저장 기간

파일 범위 객체와 `static` 지역 객체는 정적 저장 기간을 가집니다.

```c
static int count;

void increment(void)
{
    static int calls;
    ++calls;
}
```

이 객체들은 프로그램 실행 동안 저장 공간이 유지됩니다.

하지만 수명이 길다는 것과 안전하게 공유할 수 있다는 것은 다른 문제입니다.

여러 함수나 스레드가 같은 객체를 변경한다면 별도로 다음을 고려해야 합니다.

* 누가 값을 변경하는가
* 동시에 접근할 수 있는가
* 동기화가 필요한가

### 할당된 저장 공간과 수명

`malloc`, `calloc`, `realloc` 등으로 저장 공간을 동적으로 얻을 수 있습니다.

```c
int *values = malloc(count * sizeof *values);
```

할당이 성공하면 사용할 수 있는 저장 공간이 생깁니다.

해당 메모리는 적절한 `free` 또는 관련 `realloc` 동작으로 수명이 끝날 때까지 사용할 수 있습니다.

```c
free(values);
```

`free` 이후에는 `values`에 예전 주소 값이 남아 있더라도 그 메모리를 다시 읽거나 쓰면 안 됩니다.

```c
free(values);

/* 잘못된 접근 */
printf("%d\n", values[0]);
```

동적 메모리를 사용할 때는 **누가 `free`를 호출할 것인지**를 명확하게 정해야 합니다.

## 할당 크기 계산

다음 코드는 `count`개의 `int`를 저장할 공간을 요청합니다.

```c
values = malloc(count * sizeof *values);
```

하지만 `count * sizeof *values`도 `size_t` 범위 안에서 계산되는 정수 연산입니다.

`count`가 매우 크다면 곱셈이 넘칠 수 있습니다.

```c
if (count > SIZE_MAX / sizeof *values) {
    return -1;
}

values = malloc(count * sizeof *values);
```

예를 들어 실제 필요한 크기가 매우 큰데 계산이 overflow하여 작은 값으로 바뀌면 `malloc`은 예상보다 작은 메모리를 할당할 수 있습니다.

이후 코드는 `count`개의 원소가 있다고 생각하고 접근하기 때문에 버퍼 범위를 벗어날 수 있습니다.

따라서 원소 개수에서 바이트 수를 계산할 때는:

```text
원소 수 × 원소 하나의 크기
```

의 곱셈이 표현 가능한지 먼저 확인합니다.

`sizeof *values` 형태는 다음보다 일반적으로 낫습니다.

```c
sizeof(int)
```

포인터의 타입이 바뀌어도 할당할 원소 크기가 자동으로 함께 바뀌기 때문입니다.

## 크기가 0인 할당

```c
malloc(0)
```

의 반환값을 특정 값으로 가정하면 안 됩니다.

구현에 따라 `NULL`일 수도 있고, 이후 `free`할 수 있는 NULL이 아닌 값을 반환할 수도 있습니다.

따라서 자료구조가 비어 있을 때의 표현은 할당 함수의 반환값에 의존하기보다 프로그램에서 직접 정하는 것이 좋습니다.

예를 들어:

```text
빈 상태:

data == NULL
size == 0
capacity == 0
```

처럼 일관된 규칙을 사용할 수 있습니다.

그러면 빈 버퍼인지 확인하기 위해 `malloc(0)`의 구현별 동작을 고려할 필요가 없습니다.

## `realloc`

`realloc`은 기존 할당의 크기를 변경할 때 사용합니다.

```c
void *resized = realloc(data, new_size);

if (resized == NULL) {
    return -1;
}

data = resized;
```

`realloc`은 기존 위치에서 크기를 늘릴 수도 있고, 새로운 위치에 메모리를 확보하여 내용을 옮길 수도 있습니다.

따라서 성공 후 주소가 이전과 같다는 보장은 없습니다.

### 실패 시 기존 메모리 보존

다음처럼 작성하면 문제가 있습니다.

```c
data = realloc(data, new_size);

if (data == NULL) {
    return -1;
}
```

`realloc`이 실패하면 원래 할당은 그대로 남아 있지만 `data`에는 `NULL`이 저장됩니다.

그러면 원래 주소를 잃어버려 해당 메모리를 다시 접근하거나 `free`할 수도 없습니다.

따라서 임시 포인터를 사용합니다.

```c
void *resized = realloc(data, new_size);

if (resized == NULL) {
    return -1;
}

data = resized;
```

핵심 규칙은 다음과 같습니다.

> 상태 변경에 실패할 수 있다면 성공 여부를 확인하기 전에 기존 상태를 덮어쓰지 않습니다.

단, `new_size == 0`인 `realloc`은 표준 버전과 구현에 따른 세부 동작을 별도로 고려해야 합니다. 크기 0을 자료구조의 정상적인 resize 경로로 사용하기보다 직접 `free`하고 빈 상태로 만드는 편이 코드 의미가 명확합니다.

## 소유권

포인터 타입만 보고는 메모리를 누가 관리해야 하는지 알 수 없습니다.

예를 들어:

```c
void process(char *data);
```

만 봐서는 다음 중 어느 의미인지 알 수 없습니다.

* 호출자가 계속 소유하고 함수는 읽기만 함
* 호출자가 계속 소유하고 함수가 내용을 수정함
* 함수가 호출이 끝나기 전까지만 빌려 사용함
* 함수가 포인터의 소유권을 넘겨받음
* 함수 내부에서 `free`함

새 메모리를 반환하는 함수도 마찬가지입니다.

```c
char *string_copy(const char *source);
```

이 함수가 새 메모리를 할당한다면 호출자는 보통 다음 책임을 가집니다.

```c
char *copy = string_copy(source);

if (copy == NULL) {
    /* 실패 처리 */
}

/* 사용 */

free(copy);
```

이런 규칙을 흔히 **소유권(ownership)** 이라고 부릅니다.

C의 타입 시스템은 소유권을 직접 표현하지 않으므로 함수 선언만으로 충분하지 않은 경우 헤더나 문서에 명시해야 합니다.

예를 들어:

```text
string_copy:
- 새 버퍼를 할당하여 반환합니다.
- 성공 시 반환된 버퍼의 소유권은 호출자에게 있습니다.
- 호출자는 더 이상 필요하지 않을 때 free해야 합니다.
- 실패 시 NULL을 반환합니다.
```

처럼 구체적으로 작성하는 편이 좋습니다.

## 빌린 포인터와 소유한 포인터

소유권을 이해할 때 다음 두 경우를 구분하면 편합니다.

```text
소유한 포인터
→ 해당 allocation을 최종적으로 해제할 책임이 있음

빌린 포인터
→ 다른 객체가 소유한 메모리를 잠시 참조함
→ 임의로 free하면 안 됨
```

예를 들어:

```c
void print_text(const char *text);
```

에서 `text`는 일반적으로 호출자가 소유한 문자열을 잠시 전달받은 포인터입니다.

반면:

```c
char *duplicate_text(const char *text);
```

가 새 메모리를 반환하도록 설계되어 있다면 반환값은 호출자가 소유하게 만들 수 있습니다.

## 얕은 복사

다음 구조체를 생각해 봅니다.

```c
struct string {
    char *data;
    size_t length;
};
```

그리고:

```c
struct string left = right;
```

를 수행하면 구조체의 각 멤버 값이 복사됩니다.

즉 `data`가 가리키는 문자열 내용 자체가 복제되는 것이 아니라 **주소 값이 복사됩니다.**

```text
right.data ─┐
            ├──→ 같은 allocation
left.data  ─┘
```

이를 얕은 복사(shallow copy)라고 부릅니다.

만약 두 구조체를 모두 독립적인 소유자로 취급하면:

```c
free(left.data);
free(right.data);
```

같은 allocation을 두 번 해제하게 됩니다.

이는 정의되지 않은 동작입니다.

독립적인 객체 두 개가 필요하다면 실제 데이터도 별도로 복제해야 합니다.

```text
right.data ──→ allocation A
left.data  ──→ allocation B
```

이런 복사를 깊은 복사(deep copy)라고 합니다.

따라서 포인터를 멤버로 가진 구조체를 복사할 때는 단순 구조체 대입이 원하는 소유권 의미와 일치하는지 확인해야 합니다.

## 배열과 포인터 연산

배열 원소는 메모리에 연속해서 배치됩니다.

```c
int values[4];
```

`values`를 원소를 가리키는 포인터로 사용할 때:

```c
values + 1
```

은 주소에 단순히 숫자 `1`을 더하는 것이 아닙니다.

다음 원소의 위치를 가리킵니다.

개념적으로:

```text
values + 0 → values[0]
values + 1 → values[1]
values + 2 → values[2]
values + 3 → values[3]
values + 4 → 배열 바로 다음 위치
```

따라서 다음 순회가 가능합니다.

```c
for (int *cursor = values;
     cursor != values + count;
     ++cursor) {
    process(*cursor);
}
```

`values + count`는 배열의 마지막 원소 **다음 위치(one past the end)** 를 나타냅니다.

이 포인터는 반복 종료 조건처럼 계산하고 비교하는 데 사용할 수 있지만:

```c
*(values + count)
```

처럼 역참조해서는 안 됩니다.

유효한 원소는:

```text
values[0] ... values[count - 1]
```

까지입니다.

또한 C의 포인터 산술은 아무 주소끼리 자유롭게 계산하는 기능이 아닙니다. 같은 배열 객체와 관련된 범위 안에서 사용해야 합니다.

## 문자열

C 문자열은 별도의 문자열 객체 타입이 아니라 **마지막에 NUL 문자 `'\0'`가 있는 문자 배열**입니다.

예를 들어 문자열:

```text
cat
```

은 실제로 다음 네 개의 문자를 저장합니다.

```text
'c' 'a' 't' '\0'
```

따라서 길이가 `3`인 문자열을 저장하려면 최소 `4`바이트가 필요합니다.

```c
size_t length = strlen(source);
char *copy = malloc(length + 1);
```

`strlen`의 결과에는 마지막 NUL 바이트가 포함되지 않기 때문에 복사할 버퍼에는 `+ 1`이 필요합니다.

또한 `strlen(source)`를 호출하기 전에 `source`가 실제로 NUL 종료된 유효한 문자열이어야 합니다.

`strlen`은 버퍼의 최대 크기를 알지 못합니다. 지정된 메모리 범위 안에서 `'\0'`을 찾지 못하면 배열 밖을 읽게 됩니다.

## 문자열 크기의 overflow

버퍼 크기를 계산하면서 여러 길이를 더한다면 덧셈 역시 overflow할 수 있습니다.

두 문자열과 마지막 NUL을 저장하려면:

```text
left_length + right_length + 1
```

바이트가 필요합니다.

다음처럼 단계적으로 검사하는 것이 이해하기 쉽습니다.

```c
if (left_length > SIZE_MAX - right_length) {
    return -1;
}

size_t combined = left_length + right_length;

if (combined == SIZE_MAX) {
    return -1;
}

size_t required = combined + 1;
```

또는 같은 조건을 적절히 결합해서 검사할 수 있습니다.

핵심은:

> overflow가 발생한 뒤 결과를 검사하는 것이 아니라 연산하기 전에 해당 연산이 가능한지 검사합니다.

참고로 이미 정상적인 C 객체 안에서 `strlen`이 성공적으로 반환한 단일 문자열 길이에 대해 실제로 `SIZE_MAX`에 도달하는 상황은 현실적인 객체 크기 제약 때문에 사실상 문제가 되지 않습니다. 중요한 학습 포인트는 특정 `strlen` 검사 자체보다 **길이들을 조합해 새 크기를 만들 때 overflow를 막는 것**입니다.

## `memcpy`와 `memmove`

두 함수 모두 바이트 단위로 메모리를 복사합니다.

### `memcpy`

```c
memcpy(destination, source, size);
```

원본 영역과 대상 영역이 겹치지 않는다는 조건에서 사용합니다.

### `memmove`

```c
memmove(destination, source, size);
```

두 영역이 겹쳐도 올바르게 복사되도록 정의되어 있습니다.

예를 들어 같은 배열 내부에서 데이터를 앞으로 이동한다고 가정합니다.

```c
char text[] = "ABCDE";

memmove(text + 1, text, 4);
```

원본과 목적지가 같은 배열의 겹치는 부분을 사용합니다.

이런 경우 `memcpy`를 사용하는 것은 안전하지 않습니다.

```c
memcpy(text + 1, text, 4); /* 겹치는 영역: 정의되지 않은 동작 */
```

따라서 같은 버퍼 내부에서 원소를 당기거나 밀어내는 작업이라면 두 영역이 겹칠 가능성을 먼저 확인합니다.

## 별칭

둘 이상의 포인터가 같은 객체 또는 같은 메모리 영역을 가리키는 상황을 **별칭(aliasing)** 이라고 합니다.

예를 들어:

```c
char *first = buffer;
char *second = buffer + 2;
```

`first`와 `second`는 서로 다른 주소를 가지고 있지만 같은 배열의 일부를 가리킵니다.

이런 관계는 `realloc`과 함께 사용할 때 특히 주의해야 합니다.

## 별칭 입력과 `realloc`

현재 문자열 일부를 같은 문자열에 다시 덧붙이는 함수를 생각해 봅니다.

```c
append(&string, string.data + 2);
```

여기서 두 번째 인자는 `string.data`와 별개의 문자열일 수도 있지만, 위 호출에서는 현재 버퍼 내부를 가리키는 포인터입니다.

개념적으로:

```text
string.data
↓
[A][B][C][D][E][\0]
      ↑
      source
```

`append`가 공간을 늘리기 위해 다음을 수행한다고 가정합니다.

```c
realloc(string.data, new_capacity);
```

`realloc`이 새로운 주소로 데이터를 옮기면:

```text
old_data → 더 이상 유효하지 않음
new_data → 이동된 데이터
```

이 됩니다.

그러면 기존의:

```c
source = old_data + 2;
```

역시 무효가 됩니다.

따라서 `realloc` 전에 상대 위치를 보존할 수 있습니다.

```text
source_offset = source - old_data
```

그리고 성공 후:

```text
source = new_data + source_offset
```

으로 다시 계산합니다.

즉 주소 자체를 보존하는 대신 **배열 시작점에서 몇 번째 위치였는지**를 보존합니다.

### 중요한 조건

다만 다음 계산:

```c
source - old_data
```

은 아무 포인터끼리 사용할 수 없습니다.

포인터 뺄셈은 두 포인터가 같은 배열 객체 또는 그 배열 바로 다음 위치를 가리키는 경우에만 정의됩니다.

따라서 `source`가 현재 버퍼 내부를 가리킨다는 사실이 이미 확실한 경우에만 오프셋을 계산할 수 있습니다.

특히 임의의 외부 포인터를 받아서:

```c
source >= data && source < data + size
```

와 같은 관계 비교만으로 "같은 배열 안에 있는지"를 이식 가능한 C 코드에서 일반적으로 판별하려고 해서는 안 됩니다. 서로 관련 없는 객체의 포인터에 대한 순서 비교 자체가 일반적인 주소 범위 검사 수단으로 보장되지 않기 때문입니다.

따라서 실제 API 설계에서는 다음 중 하나가 더 명확할 수 있습니다.

* 내부 버퍼를 가리키는 입력이 가능한 API임을 명시하고 그 경우를 별도로 처리합니다.
* 별칭 가능 여부를 호출 규칙으로 제한합니다.
* 필요하다면 `realloc` 전에 입력 내용을 임시 저장소로 복사합니다.

## `const`

```c
size_t text_length(const char *text);
```

`const char *text`는 `text`를 통해 가리키는 문자를 수정하지 않겠다는 뜻입니다.

예를 들어 함수 안에서:

```c
text[0] = 'A';
```

처럼 수정할 수 없습니다.

하지만 `const`가 다음을 의미하는 것은 아닙니다.

* 메모리가 항상 유효함
* 문자열이 반드시 NUL 종료됨
* 배열 크기가 충분함
* 해당 메모리의 수명이 함수 호출 동안 보장됨
* 메모리를 누가 소유하는지가 결정됨
* 다른 코드가 같은 객체를 수정하지 않음

즉 `const`는 주로 **해당 포인터를 통한 수정 가능성**에 관한 타입 정보입니다.

다음 두 선언도 구분해야 합니다.

```c
const char *text;
char *const text2 = buffer;
```

첫 번째는:

```text
가리키는 char를 이 포인터를 통해 수정할 수 없음
```

두 번째는:

```text
포인터 변수 text2 자체를 다른 주소로 바꿀 수 없음
```

을 의미합니다.

```c
const char *const text3 = buffer;
```

처럼 둘을 동시에 적용할 수도 있습니다.

## 정리 함수

동적 메모리를 가진 객체는 명시적인 정리 함수를 두는 경우가 많습니다.

```c
void buffer_destroy(struct buffer *buffer)
{
    if (buffer == NULL) {
        return;
    }

    free(buffer->data);

    buffer->data = NULL;
    buffer->length = 0;
    buffer->capacity = 0;
}
```

`free(NULL)` 자체는 안전하므로 `buffer->data == NULL`을 별도로 검사할 필요는 없습니다.

정리 후 상태를:

```text
data == NULL
length == 0
capacity == 0
```

으로 되돌려 놓으면 같은 객체에 다시:

```c
buffer_destroy(&buffer);
```

를 호출하기 쉽게 만들 수 있습니다.

`free(NULL)`은 아무 동작도 하지 않기 때문에 `data == NULL` 상태에서는 다시 해제해도 문제가 없습니다.

다만 이것이 모든 이중 해제 문제를 해결하는 것은 아닙니다.

예를 들어 다른 포인터가 같은 allocation을 가리키고 있다면:

```c
char *alias = buffer.data;

buffer_destroy(&buffer);

/* alias는 이제 댕글링 포인터 */
```

`alias`에는 여전히 예전 주소가 남아 있습니다.

따라서 객체 하나의 필드를 `NULL`로 바꿔도 **다른 별칭 포인터까지 자동으로 무효화하거나 `NULL`로 바꾸지는 않습니다.**

## 메모리 오류를 볼 때 구분할 것

포인터 관련 문제는 다음처럼 구분해서 보는 것이 좋습니다.

| 문제             | 의미                                 |
| -------------- | ---------------------------------- |
| NULL 역참조       | 객체를 가리키지 않는 `NULL` 포인터를 역참조함       |
| 댕글링 포인터        | 이미 수명이 끝난 객체를 계속 가리킴               |
| use-after-free | `free` 이후 해당 메모리에 접근함              |
| double free    | 같은 allocation을 두 번 해제함             |
| 메모리 누수         | 소유한 allocation을 잃어버려 더 이상 해제할 수 없음 |
| 범위 밖 접근        | 배열이나 할당된 영역 밖을 읽거나 씀               |
| 크기 계산 overflow | 필요한 크기보다 작은 메모리가 할당될 수 있음          |
| 잘못된 별칭 처리      | 같은 메모리를 가리키는 포인터 관계를 고려하지 않음       |

이 용어들은 서로 같은 문제가 아닙니다. 오류가 발생했을 때 어떤 수명, 범위, 소유권 규칙을 위반했는지 구분해야 원인을 찾기 쉽습니다.

## 완료 기준

1. 포인터가 `NULL`이 아닌 것과 유효한 객체를 가리키는 것이 다른 이유를 설명합니다.
2. 포인터 변수, 포인터가 가리키는 객체, 객체의 수명을 구분합니다.
3. 자동 저장 기간을 가진 지역 객체의 주소를 수명이 끝난 뒤 사용하지 않습니다.
4. 동적으로 할당한 메모리에 대해 누가 최종적으로 `free`할지 정합니다.
5. 소유한 포인터와 빌린 포인터의 차이를 설명합니다.
6. 포인터 멤버를 가진 구조체의 단순 대입이 얕은 복사가 되는 이유를 설명합니다.
7. `realloc` 실패 시 기존 포인터를 보존합니다.
8. `realloc` 성공 후 주소가 바뀔 수 있다는 사실을 고려합니다.
9. 원소 수를 바이트 수로 변환할 때 곱셈 overflow를 검사합니다.
10. 문자열 버퍼에 마지막 `'\0'`을 저장할 공간까지 포함합니다.
11. 여러 길이를 더해 새 크기를 계산할 때 덧셈 overflow를 검사합니다.
12. 배열의 one-past-the-end 포인터는 비교에는 사용할 수 있지만 역참조하지 않습니다.
13. 겹칠 수 있는 메모리 영역을 복사할 때 `memmove`를 사용합니다.
14. 별칭 입력이 `realloc` 후 무효가 될 수 있는 이유를 설명합니다.
15. 같은 배열 내부의 포인터일 때만 포인터 차이를 오프셋으로 계산할 수 있음을 설명합니다.
16. `const`가 수정 가능성을 제한할 뿐 수명이나 소유권까지 보장하지 않는다는 점을 설명합니다.
17. `free` 후 한 포인터를 `NULL`로 바꿔도 다른 별칭 포인터는 여전히 댕글링 포인터가 될 수 있음을 설명합니다.
